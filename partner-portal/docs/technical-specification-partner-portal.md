# Техническое задание на информационную систему «Партнёрский портал SimbirSoft»

**Версия:** 2.0  
**Дата:** 30.09.2026  
**Статус:** проект для согласования  
**Целевой адрес:** `partner.simbirsoft.com`

## 1. Основание и приоритет решений

Документ объединяет исходное ТЗ версии 1.0, реализованный React/Vite-прототип, OpenSpec change `partner-registration`, требования к Java/Spring-разработке и решения пользователя от 30.09.2026.

При противоречии применяется следующий приоритет:

1. решения пользователя в текущем change;
2. актуальные OpenSpec-спецификации;
3. настоящее ТЗ;
4. исходное ТЗ версии 1.0;
5. поведение демонстрационного прототипа.

Зафиксированные изменения относительно исходного ТЗ:

- архитектура — модульный монолит;
- JPA/Hibernate разрешён и является основным механизмом CRUD;
- `NamedParameterJdbcTemplate + QueryHelper` применяется для сложных выборок, аналитики и массовых операций;
- хранимые процедуры и `SimpleJdbcCall` запрещены;
- партнёры входят через Yandex ID, поэтому локальные пароли, смена пароля и собственная 2FA не реализуются;
- сотрудники входят через LDAP;
- переводы и юридические тексты создаются вручную; автоматический перевод не применяется;
- production не содержит демонстрационных бизнес-данных.

## 2. Назначение и цели

Система автоматизирует взаимодействие SimbirSoft с внешними партнёрами: регистрацию, передачу и квалификацию лидов, формирование заявок на специалистов, подбор кандидатов, расчёт вознаграждений, обмен документами и внутреннюю обработку операций.

Целевые показатели:

| Цель | Показатель |
|---|---|
| Развитие партнёрского канала | не менее 30 активных партнёров за 12 месяцев |
| Прозрачность начислений | доля оспоренных начислений менее 5% |
| Скорость обработки заявок | первая реакция Production не более 24 часов |
| Международная работа | полноценные RU/KZ/EN локали |
| Безопасность | отсутствие критических инцидентов ИБ |

## 4. Архитектура и технологический стек

### 4.1. Общая архитектура

Система реализуется как модульный монолит с одним Spring Boot backend и React SPA. Доменные модули имеют независимые модели, application interfaces и владельцев таблиц. Прямое использование repository другого модуля запрещено.

Основные модули: `access`, `partner`, `lead`, `staffing`, `candidate`, `finance`, `document`, `notification`, `localization`, `audit`, `integration`.

### 4.2. Backend

- Java 21, Spring Boot 3;
- Spring MVC, Spring Validation, Spring Security;
- Spring Data JPA / Hibernate для CRUD, агрегатов, optimistic locking и связей внутри модуля;
- `NamedParameterJdbcTemplate` и проектный `QueryHelper` (`com.simbirsoft.partners.shared.persistence`) для сложных фильтров, аналитики, отчётных проекций и массовых операций;
- PostgreSQL 15+;
- Liquibase для всех изменений схемы;
- Lombok: `@RequiredArgsConstructor`, `@Builder`, `@FieldNameConstants`, `@Slf4j` и другие уместные аннотации;
- SpringDoc OpenAPI 3;
- WebClient для внешних HTTP-интеграций;
- `AbstractDbConfig` для конфигурации DataSource при необходимости корпоративной схемы конфигурации;
- Gradle как рекомендуемая система сборки.

Запрещены хранимые процедуры, `SimpleJdbcCall`, SQL-строки внутри Java, DDL вне Liquibase и бизнес-логика в контроллерах или БД.

### 4.3. Frontend

- React 18+ / текущая версия прототипа React 19;
- TypeScript при production-реализации;
- Vite;
- библиотека запросов и кеша server state;
- общая схема форм, валидации и обработки API-ошибок;
- адаптивный интерфейс от 360 px;
- WCAG 2.1 AA для основных сценариев;
- локализация RU/KZ/EN.

### 4.4. Инфраструктура

- Frontend и backend поставляются как отдельные Docker-образы;
- Docker Compose используется для локальной разработки и интеграционных проверок;
- Kubernetes для production;
- S3-совместимое объектное хранилище документов;
- секреты только через runtime environment/secret store;
- `.env` исключён из Git, `.env.example` содержит только названия и фиктивные значения.

## 5. Требования к пользовательским интерфейсам

### 5.1. Общие требования

Интерфейс сохраняет визуальную основу прототипа: боковую навигацию, верхнюю панель с локалью и профилем, карточки показателей, таблицы, статусы, модальные формы и адаптивное мобильное меню.

Каждый экран должен поддерживать состояния `loading`, `empty`, `error`, `forbidden` и отображение актуальных данных. Опасные или необратимые операции требуют явного подтверждения. Формы сохраняют введённые данные при исправимой серверной ошибке. Все интерактивные элементы доступны с клавиатуры; модальные окна удерживают фокус и закрываются по Escape.

### 5.2. Публичный лендинг

**Назначение:** объяснить условия программы и привести посетителя к регистрации.

**Состав:**

- шапка с логотипом, RU/KZ/EN, входом и регистрацией;
- первый экран с ценностным предложением;
- этапы работы партнёра;
- условия начисления вознаграждения;
- преимущества и ответы на частые вопросы;
- юридические ссылки, контакты и политика обработки ПДн;
- CTA «Стать партнёром» и «Войти».

Для RU/EN используется SimbirSoft, для KZ — 17Soft. Публичная локаль доступна только при опубликованном полном наборе текстов, оферты, согласий и логотипа.

### 5.3. Вход и регистрация партнёра

**Вход:** кнопка переводит пользователя в Yandex ID. После callback backend проверяет `state`, получает внешний subject и создаёт web-сессию.

**Шаги регистрации:**

1. выбор типа: физическое лицо, ИП или юридическое лицо;
2. страна/регион и язык;
3. идентификационные данные;
4. контактное лицо;
5. юридические и платёжные реквизиты, если применимо;
6. просмотр оферты и согласий;
7. проверка и отправка.

**Поля:** наименование/ФИО, ИНН/БИН или локальный аналог, регистрационный номер, адрес, ФИО контактного лица, email, телефон, страна, регион, банковские реквизиты и обязательные согласия. Точный состав задаётся справочником типа и юрисдикции.

**Состояния заявки:** `DRAFT`, `SUBMITTED`, `REGISTRY_CHECK`, `MANUAL_REVIEW`, `CHANGES_REQUESTED`, `APPROVED`, `REJECTED`.

До одобрения доступны только статус, сообщения проверяющего, редактирование запрошенных полей и повторная отправка. Отказ содержит безопасную причину. Повторная подача создаёт новую редакцию.

### 5.4. Обзор партнёрства

Экран содержит:

- заработанное вознаграждение;
- активный оборот;
- количество лидов в работе;
- статус аккаунта;
- последние лиды;
- задачи: кандидаты на рассмотрении, документы на согласовании, запросы уточнений и финансовые обращения;
- быстрые действия «Добавить лид» и переходы к задачам.

Каждая метрика имеет дату актуальности и строится только по данным партнёра. Значения кликабельны и открывают отфильтрованный раздел.

### 5.5. Лиды

**Список:** поиск по компании и запросу, фильтры по статусу/менеджеру/периоду, сортировка, пагинация, экспорт разрешённых данных. Колонки: номер, компания, запрос, статус, обновление, ответственный.

**Создание:**

- компания;
- домен и/или ИНН;
- описание потребности;
- предварительный бюджет и валюта;
- плановый старт;
- контакт ЛПР и email;
- комментарий;
- PDF/DOCX до 20 МБ.

**Карточка:** реквизиты, история статусов, сообщения, файлы, результат атрибуции, связанный проект и заявки на специалистов.

**Статусы:** `NEW`, `QUALIFICATION`, `DUPLICATE_REVIEW`, `IN_WORK`, `WON`, `LOST`, `REJECTED`. Партнёр не видит данные пересекающегося внутреннего клиента. Окно защиты лида по умолчанию — 6 месяцев, значение настраивается.

### 5.6. Заявки на специалистов

**Список:** номер, компания/проект, роль, грейд, статус, SLA, дедлайн, количество кандидатов.

**Создание:** связанный лид/проект, роль, грейд, стек и обязательные навыки, желательные навыки, количество специалистов, часы в неделю, формат работы, часовой пояс, язык, срок выхода, дедлайн ответа, описание и исходный файл ТЗ.

**Карточка:** требования, ответственный Resource Manager, SLA, история, сообщения, предложенные кандидаты и общий пул, если доступен.

**Статусы:** `NEW`, `CLARIFICATION`, `SEARCH`, `CANDIDATES_PROPOSED`, `INTERVIEW`, `OFFER`, `FILLED`, `CANCELLED`, `CLOSED`. Изменение существенных требований после начала поиска создаёт новую редакцию и пересчитывает SLA по утверждённым правилам.

### 5.7. Кандидаты и общий пул

Профиль кандидата для партнёра содержит псевдоним/номер, опыт, стек, краткое описание, доступность, обезличенное CV и водяной знак. ФИО, контакты и идентифицирующие работодателей сведения скрыты.

Действия партнёра:

- поиск по навыкам;
- просмотр профиля;
- запрос назначения кандидата на собственную заявку;
- фиксация `INTERVIEW`, `OFFER`, `REJECTED`;
- обязательная причина отказа.

Запрос назначения сначала получает `PENDING_CONFIRMATION`. Только Production может подтвердить доступность. Один кандидат не должен быть подтверждён в конфликтующие назначения.

### 5.8. Вознаграждения

**Сводка:** заработано, ожидается, выплачено, период и валюта.

**Таблица:** проект, период, оборот, валюта и курс, ставка, сумма, статус, дата выплаты. Доступны фильтры и экспорт.

**Статусы:** `DRAFT`, `CALCULATED`, `FIRST_APPROVED`, `APPROVED`, `TO_PAY`, `PAID`, `DISPUTED`, `CANCELLED`.

Партнёр может открыть расчёт, скачать реестр/акт и создать обращение с описанием и вложениями. Финансовое обращение имеет номер, статус, диалог и решение. Любое изменение исходных данных после подтверждения создаёт новую редакцию и повторный цикл согласования.

### 5.9. Документы

Экран показывает название, тип, связанный объект, период, версию, статус, дату и доступные действия. Поддерживаются загрузка, скачивание, предварительный просмотр безопасных форматов и согласование конкретной версии.

Типы: оферта и согласия, договор, акт сверки, финансовый реестр, ТЗ лида/заявки, анонимизированное CV и иные утверждённые типы.

Статусы: `UPLOADING`, `SCANNING`, `AVAILABLE`, `REVIEW_REQUIRED`, `APPROVED`, `REJECTED`, `QUARANTINED`, `ARCHIVED`. Файл до завершения антивирусной проверки недоступен пользователям.

### 5.10. Профиль и настройки

Раздел содержит контактные данные, тип партнёра, организацию, реквизиты, локаль и настройки уведомлений. Контактные данные меняются непосредственно с аудитом; юридические и платёжные реквизиты проходят повторную проверку. Функций локального пароля и 2FA нет.

### 5.11. Уведомления

Центр уведомлений показывает непрочитанные и архивные события: решение по регистрации, запрос уточнений, смену статуса лида, кандидата, нарушение SLA, готовность начисления/документа и ответ на обращение. Доступны переход к объекту и отметка прочитанным. Недоступный объект не раскрывается через текст уведомления.

### 5.12. Back-office: модерация партнёров

Менеджер видит очередь с фильтрами по стране, типу, статусу, результату реестра, сроку и ответственному. Карточка показывает редакцию анкеты, реквизиты, результат внешней проверки, согласия, историю, комментарии и дубликаты без избыточного раскрытия ПДн.

Действия: назначить менеджера, запросить изменения, перевести на ручную проверку, одобрить, отклонить с обязательной причиной. Решение выполняется транзакционно с optimistic locking.

### 5.13. Back-office: лиды

Доступны таблица и Kanban, атрибуция, назначение ответственного, внутренние/внешние комментарии, переходы статусов, арбитраж пересечений и связь с CRM. Внутренние комментарии никогда не выдаются партнёру.

### 5.14. Back-office: Production

Экран содержит очереди заявок, SLA-индикаторы, требования, извлечённые навыки, поиск по bench, создание предложения, загрузку и анонимизацию CV, подтверждение запроса назначения и историю решений. Результат автоматического анализа всегда подтверждается человеком.

### 5.15. Back-office: финансы

Финансовый контролёр управляет версиями ставок, импортирует оборот, проверяет расчёт, выполняет первое/второе подтверждение, формирует реестр выплат и отвечает на обращения. Импорт сначала проходит dry-run с протоколом ошибок; частичное применение ошибочного файла запрещено.

### 5.16. Back-office: локализация и администрирование

Администратор управляет:

- словарями RU/KZ/EN;
- черновиками и опубликованными версиями;
- офертами и согласиями;
- логотипами и соответствием локалям;
- импортом/экспортом JSON/XLSX;
- LDAP group-to-role mapping;
- справочниками, feature flags и состоянием интеграций;
- журналом аудита.

Публикация неполной локали запрещена. Автоматический перевод отсутствует.

## 6. Требования к API

### 6.1. Общие правила

- базовый путь `/api/v1`;
- JSON UTF-8, даты ISO 8601 UTC, денежные суммы — decimal + ISO 4217 currency;
- DTO — Java records, `@Schema` на типах и полях;
- Bean Validation для входных данных;
- OpenAPI: `@Tag`, `@Operation`, `@ApiResponses`, `@Parameter`;
- пагинация: `page`, `size`, `sort`; максимальный `size` задаётся конфигурацией;
- единая ошибка: `timestamp`, `status`, `code`, `message`, `traceId`, `fieldErrors`;
- `401` — нет аутентификации, `403` — нет полномочий, `404` — объект недоступен/не найден, `409` — конфликт версии или состояния, `422` — доменное ограничение;
- команды с риском повтора принимают `Idempotency-Key`;
- optimistic locking передаётся через version/ETag для критических операций.

### 6.2. Основные группы маршрутов

| Группа | Примеры операций |

| Dashboard | агрегированные показатели и задачи партнёра |
| Leads | список, создание, карточка, сообщения, файлы |
| Staffing | заявки, редакции требований, SLA и кандидаты |
| Candidates | пул, профиль, запрос назначения, решение |
| Finance | начисления, акты, экспорт и обращения |
| Documents | метаданные, upload-init, download и согласование |
| Notifications | список, счётчик, прочтение, настройки |
| Profile | профиль, контакты, реквизиты и локаль |
| Admin | профильные очереди, решения, роли, справочники и аудит |
| Localization | draft, preview, import/export и publish |

Полный формальный контракт генерируется SpringDoc и версионируется в репозитории.

## 8. Работа с БД

JPA entity размещаются внутри инфраструктуры владельца модуля и не используются как API DTO. Для CRUD применяются Spring Data repository. Для сложных чтений создаются query repository на `NamedParameterJdbcTemplate + QueryHelper`; SQL лежит в `src/main/resources/sql/<module>/` и вызывается с именованными параметрами.

Liquibase changeset:

- одна логическая операция на changeset;
- применённые changeset не редактируются;
- destructive изменения выполняются по expand/contract;
- индексы и ограничения создаются явно;
- migration тестируется на чистой базе и на предыдущей поддерживаемой версии.

Хранимые процедуры, функции с бизнес-логикой и `SimpleJdbcCall` не допускаются.

## 9. Интеграции

| Система | Назначение | Поведение при сбое |
|---|---|---|
| Yandex ID | внешний вход партнёров | вход отклоняется, локальная связь не меняется |
| LDAP | вход сотрудников и группы | back-office недоступен, событие аудируется |
| ФНС/eGov.kz/my.soliq.uz | проверка реквизитов | ручная проверка, не автоматический отказ |
| CRM | атрибуция и синхронизация лидов | retry/outbox, статус синхронизации виден сотруднику |
| КЭДО | договоры и акты | ручной контролируемый fallback до подключения |
| ЦБ РФ/Нацбанк РК | курсы валют | используется сохранённый утверждённый курс периода |
| S3 | файлы | операция загрузки/скачивания завершается контролируемой ошибкой |
| LLM-анализатор | извлечение навыков из ТЗ | ручной ввод; результат всегда подтверждает человек |

WebClient adapters имеют timeout, ограниченный retry, circuit breaker, метрики и маскирование данных. Секреты не передаются во frontend и не журналируются.

## 10. Безопасность и персональные данные

- TLS 1.3 на внешнем контуре;
- Secure/HttpOnly/SameSite cookie и CSRF-защита;
- RBAC и object-level authorization;
- минимизация OAuth scopes;
- шифрование чувствительных данных at rest и при передаче;
- keyed hash нормализованных реквизитов для безопасной дедупликации;
- rate limiting для входа, регистрации, поиска и загрузок;
- allow-list MIME/расширений, проверка размера и антивирус;
- WAF на внешнем контуре;
- неизменяемый аудит критических действий;
- маскирование ПДн, токенов и реквизитов в логах;
- требования 152-ФЗ и применимого законодательства РК/РУз;
- retention и удаление/обезличивание определяются утверждённой политикой данных.

## 11. Надёжность, производительность и наблюдаемость

- доступность — не ниже 99,5% в согласованное рабочее время;
- RPO ≤ 1 час, RTO ≤ 4 часа;
- PostgreSQL PITR и еженедельный полный backup;
- регулярная проверка восстановления;
- публичная часть: p95 ≤ 500 мс при профиле до 500 RPS;
- кабинет: p95 ≤ 1 с при 100 одновременных активных пользователях;
- фоновые операции не блокируют HTTP-запрос дольше настроенного timeout;
- health, readiness, liveness, метрики, structured logs и distributed traceId;
- алерты по ошибкам, latency, очереди outbox, SLA и исчерпанию ресурсов.

## 13. Тестирование

- unit tests: доменные правила, расчёты и application services;
- `@DataJpaTest`: mapping, constraints, optimistic locking;
- JDBC integration tests: реальные SQL-запросы на PostgreSQL Testcontainers;
- MockMvc: API-контракты, валидация, `401/403/404/409` и object-level access;
- WireMock: внешние HTTP adapters;
- LDAP/OAuth stubs: успешные и ошибочные сценарии;
- Playwright: регистрация, лид, заявка, кандидат, начисление, документ и RU/KZ/EN;
- migration tests: чистая и предыдущая схема;
- нагрузочное, security и accessibility тестирование перед production.

CI не требует production credentials и использует только вымышленные данные.

## 14. Этапы реализации

1. Каркас модульного монолита, CI/CD, DataSource, Liquibase, безопасность и наблюдаемость.
2. Публичная часть, Yandex ID, регистрация, LDAP и модерация.
3. Профиль, дашборд, лиды и CRM-атрибуция.
4. Заявки, Production, кандидаты и документы.
5. Финансы, двойное подтверждение, обращения и КЭДО.
6. Локализация, отчётность, hardening и промышленный запуск.

Каждый этап начинается с одобренного OpenSpec change и заканчивается тестовыми доказательствами и обновлением документации.

## 15. Критерии приёмки

Система принимается, если:

- реализованы и подтверждены сценарии утверждённых OpenSpec specs;
- роли не получают доступ к чужим или запрещённым данным;
- интерфейсы имеют loading/empty/error/forbidden состояния и работают на desktop/mobile;
- OpenAPI соответствует фактическому API;
- все миграции воспроизводимы, хранимые процедуры отсутствуют;
- unit/integration/e2e проверки проходят;
- нет Critical/High дефектов и уязвимостей;
- достигнуты согласованные нагрузочные показатели;
- backup/restore подтверждены протоколом;
- подготовлены руководство пользователя, администратора, инструкция развёртывания, политика ИБ и журнал изменений.

## 16. Ограничения и внешние зависимости

До production должны быть предоставлены и утверждены:

- OAuth-приложение Yandex ID и callback URLs;
- LDAP endpoint, bind-конфигурация и group mapping;
- доступы и правила использования государственных реестров;
- RU/KZ/EN тексты, оферты и согласия;
- логотип 17Soft и правила брендинга;
- CRM и выбранная КЭДО;
- политика хранения ПДн и документов;
- финансовые правила, валюты, округление и двойное подтверждение;
- S3, антивирус и production secret store.

Функции, требующие неподтверждённого внешнего провайдера, включаются feature flag только после contract и security review.
