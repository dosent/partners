# Модель заявки партнёра. План реализации

> **Для исполнителя:** выполнять задачи последовательно, тест сначала, затем минимальная реализация; каждый законченный этап коммитить.

**Цель:** сохранить заявки партнёров, неизменяемые редакции, юридические согласия и историю статусов с защитой от потерянных конкурентных обновлений.

**Архитектура:** модуль `partner` владеет JPA-агрегатом, таблицами и репозиториями. Заявка содержит идентификатор владельца и текущий статус; редакции, согласия и переходы статусов сохраняются отдельными append-only записями. Чувствительные реквизиты хранятся зашифрованными, а ключевой хеш нормализованного налогового номера используется для поиска дубликатов.

**Технологии:** Java 21, Spring Boot 3, Spring Data JPA, Liquibase, PostgreSQL, JUnit 5.

**Спецификация:** `openspec/changes/full-partner-portal-specification/specs/public-registration-access/spec.md`, `openspec/changes/full-partner-portal-specification/specs/platform-quality-security/spec.md`, `openspec/changes/full-partner-portal-specification/design.md`.

## Общие ограничения

- Система использует PostgreSQL 15+ и Liquibase; применённые changeset не изменять.
- Изменяемый агрегат использует `@Version`; история редакций, согласий и статусов append-only.
- Не хранить пароли, OAuth-токены, полные реквизиты в логах или открытом виде.
- Production не содержит демонстрационных бизнес-данных; юридические тексты не выдумывать.
- Документация и спецификации на русском; DTO не раскрывают JPA-сущности.

## Риски для проверки

- Налоговый номер не должен появляться в SQL-логах и исключениях; тестировать только фиктивным значением.
- Физлицо не должно требовать налоговые/компанейские поля; тестировать инварианты типов партнёра.
- Повторное сохранение редакции/согласия/статуса не должно переписывать историю.
- Два обновления одной версии не должны молча затирать друг друга.
- Недостаточная или некорректная криптографическая конфигурация должна завершаться безопасным отказом, а не записью открытого текста.
