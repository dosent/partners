# E2E-проверки и интеграция функций через worktree

## Цель

Сделать критические пользовательские потоки партнёрского портала воспроизводимо проверяемыми в браузере и закрепить единый порядок разработки: изолированная feature-ветка в отдельном Git worktree, успешные e2e-проверки и только затем коммит интеграции в `main`.

## Текущее состояние

Frontend использует React/Vite. В `package.json` есть только проверка Sites; Playwright не настроен. Backend уже имеет unit-, API-, persistence- и архитектурные тесты. Текущие реализованные пользовательские потоки включают публичный лендинг и регистрацию партнёра, кабинет и статус заявки, LDAP-вход сотрудников, состояние `ACCESS_PENDING`, управление назначениями RBAC, модерацию заявок и редактор регистрационного контента.

Yandex ID и корпоративный LDAP являются внешними зависимостями. E2E-набор не должен обращаться к production или требовать реальные учётные данные.

## Решения

### 1. Тестовый уровень

Добавить Playwright для браузерных сценариев, выполняемых против собранного приложения с настоящим backend и PostgreSQL. Проверки должны проходить через интерфейс и HTTP API; unit- и MockMvc-тесты остаются отдельными уровнями.

Для тестового окружения предусмотреть изолированные тестовые адаптеры внешней аутентификации. Они включаются только явным тестовым профилем/Compose-конфигурацией и не собираются/не включаются в production-конфигурацию. Тестовые данные и сессии должны быть предсказуемыми и сбрасываемыми. Реальные Yandex/LDAP секреты не используются.

### 2. Обязательное покрытие функций

Каждая новая или изменённая функция должна иметь e2e-сценарий на основной пользовательский путь. Для функций с разграничением доступа либо изменением состояния дополнительно проверяются существенные отказы: отсутствие роли, неверное состояние, ошибка/конфликт или безопасная недоступность зависимости — в соответствии с поведением функции.

Начальный набор покрывает существующие доступные потоки: публичный вход и навигацию, подачу и просмотр статуса заявки, кабинет одобренного партнёра, вход сотрудника и `ACCESS_PENDING`, назначение ролей, модерацию, редактирование и публикацию регистрационного контента. Где внешний поставщик не участвует в тесте, тестовый адаптер должен сохранять реальную серверную авторизацию, доменную логику и persistence.

### 3. Git/worktree поток

Для каждой функции создавать ветку `codex/<краткое-имя>` и связанный worktree от актуального `main`. Изменения и проверки выполняются в этом worktree; рабочее дерево `main` не используется для разработки функции.

Порядок интеграции:

1. Подготовить изменения и нужные unit/API/integration/e2e проверки в feature worktree.
2. Запустить обязательные e2e-сценарии и убедиться, что они прошли.
3. Зафиксировать проверенные изменения в feature-ветке.
4. Интегрировать feature-ветку в `main` и создать коммит в `main` только после успешного e2e-прогона.

При падении e2e интеграционный коммит в `main` не создаётся; исправление и повторный полный применимый прогон выполняются в feature worktree. Push в remote — отдельное действие и не является частью локального требования о коммите в `main`.

### 4. Запуск и диагностика

Добавить единые команды для установки браузеров, запуска полного e2e-набора и запуска выбранного сценария. В CI должны подниматься изолированные зависимости, собираться приложение, выполняться e2e и сохраняться отчёт/trace при ошибке. Production Compose и production secret configuration не переиспользуются для тестовой аутентификации.

## Границы

- Не менять бизнес-правила регистрации, RBAC, модерации или публикации контента.
- Не проверять реальные внешние аккаунты сотрудников/партнёров в CI.
- Не считать компонентные тесты или проверки Sites заменой пользовательским e2e.
- Не выполнять push автоматически после локального коммита в `main`.

## Критерии готовности

- Спецификация проекта требует e2e для каждой новой/изменённой функции и определяет значимые негативные сценарии.
- Описанный worktree/Git-порядок требует прохождения применимых e2e до коммита интеграции в `main`.
- Текущие реализованные основные пользовательские потоки покрыты автоматическими браузерными сценариями.
- E2E запускаются воспроизводимо без production credentials и изолированы от боевых данных.
- CI запускает обязательный набор и сохраняет диагностику неуспешных прогонов.
