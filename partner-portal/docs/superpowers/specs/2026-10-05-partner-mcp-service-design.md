# Дизайн отдельного MCP-сервиса для партнёров

## Контекст и цель

Партнёры должны подключать внешние MCP-клиенты к функциям своего кабинета. MCP публикуется как отдельный сервис и расширяется вместе с REST API портала. Права на данные и бизнес-правила остаются в backend портала.

В текущем репозитории есть React/Vite SPA и backend на Java 21 / Spring Boot 3 с модульной архитектурой. Уже реализованы партнёрские API профиля, заявки и лидов; другие разделы портала и их серверные API добавляются поэтапно. Поэтому MCP публикует только те функции, которые уже доступны через backend и явно размечены для MCP.

Партнёрские MCP-подключения используют ключи, которыми партнёр управляет в кабинете. Все ключи имеют полный набор операций партнёра; область данных всегда ограничена самим партнёром. Разделение операций на отдельные права для каждого ключа не входит в первую версию.

## Цели

- Развернуть MCP-сервис отдельным Docker-сервисом с HTTP endpoint `/mcp`.
- Предоставить партнёрам управление ключами в кабинете: создать, увидеть секрет один раз, просмотреть список и отозвать.
- Использовать OpenAPI как источник для описания доступных MCP-инструментов.
- Публиковать только явно помеченные и поддерживаемые операции backend.
- Сохранить backend единственным владельцем аутентификации партнёра, бизнес-логики и проверки доступа к его данным.
- Добавлять простые совместимые функции через расширение backend API и MCP-метаданных; для сложных функций поддержать отдельные адаптеры в MCP-сервисе.

## Не входит в цель

- MCP-доступ сотрудников SimbirSoft и административные операции.
- Прямой доступ MCP-сервиса к PostgreSQL или JPA-репозиториям.
- Самостоятельная реализация бизнес-логики доменных модулей внутри MCP.
- Отдельные наборы permissions/scopes для разных ключей.
- Доступ через операции backend, не размеченные для MCP.
- Подмена или обход авторизации backend проверками на стороне MCP.

## Рассмотренные варианты

1. **Отдельный MCP-адаптер над REST API — выбран.** Он публикует инструменты из OpenAPI-каталога и вызывает существующие backend API. Это соблюдает требование отдельного сервиса и сохраняет одно место для бизнес-правил и проверок доступа.
2. **MCP внутри Spring Boot backend.** Упростил бы прямой вызов application-сервисов, но не был бы отдельным сервисом.
3. **Самостоятельная реализация MCP с прямым доступом к базе или привилегированным API.** Дублировала бы бизнес-логику и создавала бы обходной путь вокруг существующих правил доступа.

## Архитектура

```text
Партнёрский кабинет ── создать / отозвать ключ ──> Portal backend
                                                       │
                                                       ├── таблица ключей (хранится только хеш)
                                                       └── OpenAPI + MCP-метаданные

MCP-клиент ── HTTP + ключ ──> Отдельный MCP Docker-сервис
                                      │
                                      └── HTTP REST + тот же ключ ──> Portal backend
                                                                       │
                                                                       ├── проверка ключа
                                                                       ├── partner principal / owner scope
                                                                       └── обычные application services
```

MCP-сервис является stateless HTTP-адаптером и не подключается к PostgreSQL. Клиентский ключ передаётся в отдельном заголовке `X-Partner-API-Key`, не в URL и не как `Authorization: Bearer`. MCP-сервис не сохраняет ключ между запросами и передаёт его backend для проверки. Backend формирует обычный партнёрский security principal и применяет существующие серверные проверки владельца данных.

Авторизация статическим ключом является выбранным для продукта собственным способом подключения и не реализует OAuth-авторизацию MCP. Ключ не следует представлять как OAuth access token или передавать через `Authorization: Bearer`. У MCP-клиентов различается поддержка статических HTTP-заголовков; до production-включения необходимо проверить подключение в целевых клиентах. Если клиент не поддерживает настройку такого заголовка, это ограничение совместимости, а не повод ослаблять проверки backend.

## Управление ключами

### Жизненный цикл

- Партнёр входит в кабинет обычным способом и открывает раздел API/MCP-ключей.
- При создании он задаёт название интеграции. Backend генерирует криптографически случайный секрет высокой энтропии, связывает его с текущим партнёром и показывает секрет только в ответе создания.
- В базе сохраняются идентификатор, короткий префикс для отображения/поиска, криптографический хеш, владелец, название, время создания, последнее использование и время отзыва. Исходный секрет повторно не показывается и не сохраняется.
- Партнёр может иметь несколько ключей и отзывать их независимо. Отзыв действует на последующие запросы.
- Список показывает название, префикс, даты и состояние ключа, но не полный секрет.

### Границы доступа

- Управление ключами доступно только аутентифицированному партнёру и работает с ключами из его собственного owner scope.
- Каждый ключ предоставляет все текущие и будущие операции, доступные партнёру, в пределах прав самого партнёра.
- Переданный в URL, теле или аргументах инструмента идентификатор партнёра не меняет owner scope.
- MCP-инструменты не получают сотруднические или административные права.

### Обработка секрета

- MCP-клиент отправляет ключ только в заголовке `X-Partner-API-Key` поверх TLS.
- Ключ нельзя писать в application/access log, trace, метрики, URL или сообщения об ошибках.
- MCP-сервис передаёт его backend только для текущего вызова. Backend проверяет хеш и статус отзыва при запросах, а не полагается на локальный кеш, который задержал бы отзыв.
- Журналирование успешных действий использует идентификатор ключа/партнёра, имя MCP-инструмента и trace ID без секрета и бизнес-payload.

## MCP-каталог и разметка backend API

OpenAPI остаётся контрактом REST API, а отдельные метаданные помечают разрешённые MCP-операции. По умолчанию любой новый REST endpoint закрыт для MCP.

### Требуемое developer-документирование

В backend README и руководстве по MCP-интеграции нужно описать обязательную процедуру публикации операции:

1. Реализовать обычный партнёрский endpoint и application use case по правилам модульного монолита.
2. Убедиться, что операция проверяет право, owner scope и состояние объекта в backend.
3. Указать в OpenAPI стабильные `operationId`, краткое имя и полезное описание.
4. Добавить явную аннотацию `@McpTool` к методу контроллера.
5. Убедиться, что генератор/настройка SpringDoc экспортирует метаданные аннотации как расширение OpenAPI `x-mcp`.
6. Добавить контрактные проверки, что размеченная операция появляется в MCP-каталоге, неразмеченная — отсутствует, а схема аргументов соответствует DTO.
7. Для неподдерживаемого generic-вызовом поведения (multipart upload, потоковая передача, многошаговая операция и т. п.) добавить именованный адаптер MCP и задокументировать его контракт.

Эскиз желаемого кода (точная Java-сигнатура и способ подключения SpringDoc уточняются в implementation plan):

```java
@McpTool(
    name = "partner_lead_create",
    description = "Создать лид в кабинете партнёра",
    behavior = McpToolBehavior.MUTATING
)
@PostMapping
public LeadResponse createLead(@Valid @RequestBody CreateLeadRequest request) {
    // Контроллер делегирует application service как обычно.
}
```

OpenAPI-адаптер преобразует эту аннотацию в расширение операции, концептуально содержащее:

```yaml
x-mcp:
  enabled: true
  name: partner_lead_create
  description: Создать лид в кабинете партнёра
  behavior: mutating
```

Схема `inputSchema` строится из существующих OpenAPI path/query parameters и JSON request body. Имена инструментов должны быть стабильны и не содержать версии REST path. Описания должны объяснять назначение операции понятным для MCP-клиента языком. Каталог не должен автоматически открывать весь OpenAPI.

Для операций с вложенными объектами, файлами, нестандартным вводом или сложными результатами применяется адаптер MCP, который преобразует MCP schema/result в существующий REST контракт. Адаптер не реализует доменные правила.

## Поток вызова

1. Клиент соединяется с endpoint `/mcp` по Streamable HTTP и передаёт настроенный статический API-ключ в `X-Partner-API-Key`.
2. На `tools/list` MCP-сервис возвращает только операции из разрешённого `x-mcp` каталога.
3. На `tools/call` MCP-сервис проверяет имя инструмента и аргументы по опубликованной схеме; произвольные URL/method от клиента не принимаются.
4. MCP-сервис вызывает соответствующий REST endpoint backend с тем же ключом в `X-Partner-API-Key` и аргументами.
5. Backend валидирует ключ, строит principal партнёра и запускает обычный application use case. Все проверки владельца, ролей, статуса и данных выполняются в backend.
6. MCP-сервис преобразует стандартный ответ/error envelope backend в MCP result/error, не меняя бизнес-смысл.

Проверка схемы в MCP — дополнительная валидация формата, не механизм авторизации. Backend остаётся доверенной границей.

## Обновление каталога и совместимость API

- MCP-сервис получает опубликованный OpenAPI-контракт backend по внутреннему URL и строит из него каталог инструментов.
- Спецификация и каталог версионируются; MCP-сервис проверяет контракт при старте/обновлении и не публикует некорректную или неподдерживаемую операцию.
- Простая новая операция обычно требует изменения backend endpoint, `@McpTool` и OpenAPI; изменения Java-кода MCP-сервиса не требуется, если операция укладывается в поддерживаемое преобразование.
- Сложная операция требует дополнительно реализовать/обновить адаптер MCP и выпустить образ MCP-сервиса.
- Удаление, переименование инструмента и несовместимое изменение схемы должны проходить контролируемый переход с периодом совместимости либо явной версией инструмента.
- MCP-перечень не должен включать администраторские, публично-регистрационные или сотруднические операции только потому, что они присутствуют в том же OpenAPI.

## Развёртывание

- Добавить отдельный `mcp` service в Docker Compose и отдельный production Docker image.
- MCP получает URL backend/OpenAPI и необходимые runtime-параметры через переменные окружения; секреты не включаются в image, исходники или frontend bundle.
- В production внешний доступ проходит через HTTPS ingress на отдельном hostname или выделенном пути. Внутренние вызовы backend идут по service network.
- MCP не получает DB credentials и не монтирует файлы приложения.
- Развёртывание backend и MCP может идти разными релизами; порядок релизов и допустимые версии OpenAPI фиксируются контрактной проверкой.

## Ошибки, аудит и эксплуатация

- Недействительный или отозванный ключ возвращает отказ аутентификации; объект вне owner scope — отказ доступа, как и в обычном REST API.
- MCP сохраняет машинный код ошибки backend и безопасное сообщение, добавляет trace ID, но не раскрывает stack trace, ключ, PII или содержимое документов.
- Таймаут backend, временная ошибка upstream и невалидный MCP-каталог обрабатываются отдельно; повтор автоматически разрешён только для безопасных чтений. Изменяющие вызовы не повторяются без идемпотентного контракта.
- Backend фиксирует успешные критические изменения в имеющемся аудите. MCP использует сквозной trace ID; в эксплуатационных метриках допускаются имя инструмента, статус, длительность, партнёр/идентификатор ключа, но не секрет и не аргументы с бизнес-данными.
- Нужны ограничение частоты вызовов на ключ/партнёра и разумные лимиты размера аргументов/ответа; значения и механизм лимитов устанавливаются при реализации и нагрузочной проверке.

## Тестирование и критерии готовности

- Проверка генерации, однократного показа, хешированного хранения, листинга и немедленного отзыва API-ключа.
- API тесты авторизации: нет ключа, ошибочный/отозванный ключ, ключ другого партнёра, попытка обратиться к чужому объекту.
- MCP contract tests для `tools/list` и `tools/call`, соответствия схем OpenAPI и `x-mcp`, скрытия немаркированных endpoint и преобразования ошибок.
- WireMock/contract tests для HTTP-вызовов MCP → backend, включая timeout и upstream failure.
- E2E: партнёр создаёт ключ, подключённый MCP-клиент вызывает разрешённую операцию, второй партнёр не видит чужие данные, отзыв ключа останавливает дальнейшие вызовы.
- Проверка работы в конкретных MCP-хостах, которые будут поддерживаться партнёрами; подтвердить настройку custom HTTP header/API key до объявления совместимости.
- Интеграционные проверки backend и браузерный E2E следуют требованиям AGENTS.md: Docker Compose с PostgreSQL и вымышленными данными; production credentials запрещены.

## Этапы реализации

1. Зафиксировать внешний контракт `@McpTool`/`x-mcp`, модель ключа и security principal в OpenSpec.
2. Добавить backend CRUD/issue/revoke ключей, миграцию Liquibase, аутентификацию ключом и UI управления в кабинете партнёра.
3. Добавить явную MCP-разметку выбранных уже работающих партнёрских REST-операций и примеры для разработчиков в backend README.
4. Создать отдельный MCP Docker-сервис с OpenAPI-каталогом, generic JSON REST adapter и необходимыми custom adapters.
5. Подключить Compose, production ingress/config, метрики и аудит; провести contract, security и browser E2E проверки.
6. Расширять каталог вертикально с каждым новым партнёрским REST use case.

## Риски и решения

| Риск | Решение |
|---|---|
| Некоторые MCP-хосты не позволяют задать пользовательский HTTP-заголовок | До production зафиксировать целевые хосты и проверить подключение ключом; заявлять поддержку только проверенных клиентов. |
| MCP становится confused deputy с привилегиями backend | MCP не использует общий privileged identity; backend получает партнёрский ключ и сам строит principal/owner scope. |
| Случайное раскрытие API операции | MCP публикует только `@McpTool`/`x-mcp`; default deny и contract test на немаркированную операцию. |
| Утечка секрета через логи/trace | Хешированное хранение; фильтрация auth headers; отсутствие аргументов и секрета в логах. |
| Изменение REST схемы незаметно ломает MCP-клиентов | Проверка diff OpenAPI, проверка каталога и правила совместимости/версирования до выпуска. |
| Новая функция ещё не существует в backend | MCP не имитирует её; инструмент публикуется после появления серверного use case и REST контракта. |
