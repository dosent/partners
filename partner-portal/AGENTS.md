# Инструкции по проекту

## Правила для агентов

Документацию проекта по умолчанию пиши на русском языке: это относится к README, артефактам OpenSpec, планам и техническим заметкам для пользователей. Используй другой язык только по просьбе пользователя. Не переводи идентификаторы кода, поля API, термины протоколов и синтаксис, необходимый инструментам. В OpenSpec оставляй на английском структурные заголовки и ключевые слова, например `## Purpose`, `## ADDED Requirements`, `### Requirement`, `#### Scenario`, `WHEN`, `THEN`, `SHALL` и `MUST`, чтобы инструменты могли их обработать; пояснения и текст сценариев пиши на русском.

Перед любой реализацией или изменением поведения обязательно сверься с архитектурой приложения. Изучи актуальные архитектурные документы и OpenSpec `design.md`, а также существующую структуру кода, границы модулей, потоки данных, API и принятые в кодовой базе шаблоны. Не делай вывод об архитектуре только по этому файлу или по технологическому стеку. Если отдельного актуального архитектурного документа нет, зафиксируй это и определи архитектурный контекст по коду и действующим решениям OpenSpec.

До написания кода проверь, что предлагаемое решение соответствует текущей архитектуре. Если требования задачи ей противоречат или требуют нового архитектурного решения, сначала опиши расхождение и обнови/создай соответствующее архитектурное решение в OpenSpec; не обходи архитектуру локальным исключением. Прочитай этот файл и относящиеся к задаче актуальные артефакты OpenSpec. Описывай новую функциональность в OpenSpec. Не начинай реализацию, пока пользователь не ознакомился с текстом спецификации и не одобрил его. При изменении решений поддерживай согласованность proposal, design, specs и tasks.

Соблюдай утверждённые решения по партнёрскому порталу: партнёры сначала входят через Yandex ID; архитектура должна допускать добавление других провайдеров. Сотрудники SimbirSoft входят через LDAP. Не добавляй локальные пароли партнёров, 2FA или подтверждение электронной почты без нового требования, одобренного пользователем.

Поддерживай RU/KZ/EN. Переводы редактируются людьми через интерфейс администратора: не используй машинный перевод и не придумывай утверждённые тексты. Для RU и EN используется бренд SimbirSoft, для KZ — 17Soft. Не составляй текст оферты или согласия самостоятельно: юридические тексты для каждой локали должны быть предоставлены и утверждены до публикации. Не включай регистрацию в production, пока не настроены тексты локалей, версии оферт, логотипы и параметры интеграций.

В production не должно быть демонстрационных бизнес-записей. Данные вносятся через интерфейс продукта; тестовые данные допустимы только в средах разработки или демонстрации. Разделы портала за пределами утверждённого изменения оставляй пустыми, пока для них не появятся отдельные требования.

При реализации серверной части соблюдай утверждённую техническую основу: React/Vite, Java 21 со Spring Boot 3, PostgreSQL 15 или новее, REST API с префиксом `/api/v1` и OpenAPI. Сервисы должны запускаться в Docker; для локальной разработки и тестов настрой Docker Compose. Передавай секреты только через переменные окружения, поступающие из локального `.env` (который исключён из Git) или из хранилища секретов окружения. В репозитории разрешён только `.env.example` с пустыми или фиктивными значениями. Не встраивай секреты в исходники, Dockerfile, образы, frontend bundle или журналы.

## Архитектура backend

Backend проектируй как модульный монолит. Верхнеуровневые предметные модули: `access`, `partner`, `lead`, `staffing`, `candidate`, `finance`, `document`, `notification`, `localization`, `audit`, `integration`. Внутри каждого модуля используй слои `api`, `application`, `domain`, `infrastructure`. Модуль не должен обращаться напрямую к repository или JPA entity другого модуля; используй его application interface или доменное событие. Проверяй границы ArchUnit-тестами.

Контроллеры не содержат бизнес-логику: принимают и валидируют transport DTO, вызывают application service и преобразуют ответ. Проверки прав, владельца и области данных выполняются сервером в security/application policy. Не считай скрытие кнопок во frontend механизмом авторизации.

API DTO реализуй Java records с `@Schema`; JPA entity не передавай через API и не используй как межмодульный контракт. Все прикладные маршруты размещай под `/api/v1`. Документируй контроллеры через SpringDoc (`@Tag`, `@Operation`, `@ApiResponses`, `@Parameter`). Используй единый формат ошибок с машинным `code`, безопасным `message`, `traceId` и ошибками полей.

## Работа с данными

Spring Data JPA/Hibernate разрешён и является основным механизмом для CRUD, агрегатов, связей и optimistic locking. Размещай JPA entity и repository в `infrastructure` соответствующего модуля. Для изменяемых агрегатов используй `@Version`; критические переходы состояний должны возвращать конфликт при конкурентном изменении.

Используй `NamedParameterJdbcTemplate` и проектный `QueryHelper` (`com.simbirsoft.partners.shared.persistence`) для сложных фильтров, дашбордов, отчётных проекций и массовых операций, когда JPA создаёт неясный или неэффективный запрос. Храни SQL только в `src/main/resources/sql/<module>/`, регистрируй его через enum, реализующий `SqlQuery`, и передавай параметры именованно. Не размещай SQL-строки в Java-коде.

Хранимые процедуры в проекте запрещены. Не добавляй `SimpleJdbcCall`, procedure/function с бизнес-логикой, каталоги процедур или вызовы хранимых процедур. Бизнес-операции выполняются в application/domain слоях и обычных параметризованных SQL-запросах.

Все DDL-изменения выполняй только новыми Liquibase changeset. Не редактируй уже применённые changeset. Для несовместимых изменений используй expand/contract. Проверяй миграции на чистой базе и на предыдущей поддерживаемой версии.

## Транзакции, интеграции и файлы

Application service владеет транзакцией use case. `@Transactional` ставь на изменяющие операции, read-only запросы помечай явно при необходимости. Смешивай JPA и JDBC в одной транзакции только при общем DataSource/transaction manager и с интеграционным тестом.

HTTP-интеграции инкапсулируй за интерфейсами и реализуй через WebClient. Настраивай timeout, retry только для безопасных операций, circuit breaker и метрики. Не логируй токены, полные реквизиты, ПДн и содержимое документов. Для доменных событий и внешней доставки используй transactional outbox; сбой уведомления не должен откатывать завершённую бизнес-операцию.

Файлы храни в S3-совместимом объектном хранилище, а в PostgreSQL — метаданные, версии, checksum, MIME-тип, размер, владельца и статус проверки. Перед выдачей файла проверяй доступ к связанному доменному объекту. Ограничивай тип и размер, выполняй антивирусную проверку.

## Тестирование backend

Покрывай domain/application логику unit-тестами JUnit 5 + Mockito. JPA mapping и repository проверяй через `@DataJpaTest`; JDBC-запросы и смешанные транзакции — интеграционно на PostgreSQL Testcontainers. Контроллеры и авторизацию проверяй MockMvc, внешние HTTP adapters — WireMock/contract tests, критические пользовательские потоки — e2e. CI должен работать без production credentials и только с вымышленными данными.

Для каждой новой функции или изменения поведения добавляй браузерный e2e-сценарий основного успешного пути. Проверяй существенные отказы по доступу, состоянию или интеграции, если они относятся к функции. Запускай e2e на собранном frontend с настоящими backend и PostgreSQL в отдельном Compose-проекте. Тестовые адаптеры внешней аутентификации допускаются только в явной e2e-конфигурации и не должны попадать в обычный production-артефакт; реальные аккаунты, production-секреты и данные запрещены. Unit-, API-, компонентные и Sites-проверки не заменяют обязательный e2e. CI должен запускать полный набор и сохранять отчёт, trace, снимки экрана при сбое и журналы сервисов без секретов и ПДн.

Перед завершением изменения запускай применимые unit, integration, architecture, frontend и OpenSpec validation проверки. Не заявляй об успешном результате без фактического вывода команд.

## Разработка и интеграция функций

Для каждой новой или меняющей поведение функции создавай отдельную ветку `codex/<краткое-имя>` и связанный worktree от актуальной `main`. Выполняй изменения и проверки в feature worktree. После применимых unit/API/integration-проверок запусти обязательный браузерный e2e-набор. Только после его успешного завершения коммить проверенные изменения в feature-ветку и интегрируй их отдельным коммитом в `main`. При падении e2e исправь проблему и повтори прогон в feature worktree; интеграционный коммит в `main` до успешного e2e запрещён. Push в remote является отдельным действием.

## Работа с прототипом

Самостоятельно запускай локальный сервер и открывай предварительный просмотр в доступном браузере. Не проси пользователя запускать сервер, если можешь сделать это сам.

Перед крупными визуальными изменениями, если источник дизайна неясен или уже не соответствует текущей задаче, используй навык `get-context` плагина Product Design. Если пользователь сообщает устойчивые предпочтения или решения по дизайну прототипа, зафиксируй их в `AGENTS.md`.

Если реализуешь выбранный сгенерированный макет, считай его эталоном расположения и состава компонентов, плотности, отступов, цветов, типографики, видимого содержимого и визуальной иерархии.

Создавай интерфейс приложения в `src/`. Не изменяй `.openai/hosting.json`, `worker/index.js`, `scripts/prepare-sites-build.mjs` и `tests/sites-worker.test.mjs`, чтобы этот локальный прототип можно было передать в Sites. Перед передачей в Sites запусти `npm run build` и `npm run test:sites`; после сборки должны существовать `dist/client/index.html`, `dist/server/index.js` и `dist/.openai/hosting.json`.
