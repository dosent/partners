## Context

Текущий проект — React/Vite SPA с демонстрационными данными в памяти браузера; server API, постоянного хранения, аутентификации и back-office нет. Целевой технологический стек и интеграции заданы в ТЗ. См. `proposal.md` и capability specs для согласованного поведения.

## Goals / Non-Goals

**Goals:**

- Добавить реальный сквозной onboarding с минимально необходимым хранением идентичности, заявок, согласий, локализованного контента и решений.
- Ограничить доступ к кабинету до одобрения и не выдавать реальные production-сессии на основе demo fixtures.
- Поддержать дальнейшее добавление внешних identity providers без смены модели партнёра.

**Non-Goals:**

- Подключение production-хранилища для лидов, заявок на специалистов, кандидатов, финансов и документов.
- Регистрация паролем, отдельная проверка email, 2FA, уведомления по email/SMS, CRM, КЭДО и автоматический перевод.
- Автоматический выпуск или юридическая генерация оферты.

## Decisions

### 1. Сквозной веб-поток и backend

Оставить существующий React/Vite клиент и добавить backend-модуль Java 21 / Spring Boot 3 с REST API `/api/v1/...` и PostgreSQL 15+, используя Spring Security, Spring Data JPA и управляемые миграции схемы. Клиент, публичная регистрация, кабинеты и back-office работают на одном сайте; сервер является источником истины для статусов и прав доступа. Это соответствует ТЗ и позволяет внедрить серверную авторизацию без переноса frontend в другой фреймворк. Отдельный BaaS или новый identity platform не выбирается: в ТЗ уже задан backend-стек и требуемые внешние сервисы.

Внешние операции проходят через один origin и backend session. React не хранит секреты Yandex ID или LDAP. Для локальной разработки предоставляется непроизводственная конфигурация PostgreSQL и тестовый LDAP adapter; она не создаёт партнёров или бизнес-данные.

Приложение и его backend должны собираться и запускаться в Docker. Для локальной разработки и интеграционных тестов использовать Docker Compose, чтобы поднимать необходимые сервисы и зависимости, включая PostgreSQL и тестовые адаптеры интеграций. Секреты передавать контейнерам только во время запуска через переменные окружения; локальные значения хранить в неотслеживаемом Git файле `.env`, а в репозитории поддерживать `.env.example` только с описанием ключей и пустыми/фиктивными значениями. В production значения предоставляет секрет-хранилище или защищённая конфигурация платформы оркестрации. Запрещено включать секреты в Git, Dockerfile, слои/образы контейнеров, клиентскую сборку или логи.

### 2. Идентификация партнёра и вход сотрудника

В первой версии использовать Yandex ID OAuth 2.0 для партнёров. Backend инициирует authorization-code flow и callback, проверяет `state`, обменивает код на стороне сервера и получает идентификатор через API Yandex ID. Идентификатор партнёра хранить в обобщённой таблице внешних identities (`provider`, `subject`), чтобы позднее добавить другой provider без изменения таблицы заявок. Контактный email и телефон вводятся в форме отдельно; email claim и доступ к остальным личным данным Yandex ID не запрашивать без необходимости. OAuth access token не сохранять после получения идентификатора. Описание протокола и прав API: [Yandex ID OAuth 2.0](https://yandex.ru/dev/id/doc/ru/) и [поля и разрешения ответа профиля](https://yandex.ru/dev/id/doc/ru/user-information).

Для сотрудников использовать LDAP-аутентификацию, сопоставляя LDAP-группы с внутренними ролями менеджера партнёров и системного администратора через deployment-конфигурацию. Это отделяет корпоративные учётные данные от партнёрских и не требует локального пароля партнёра. Пароли сотрудников также не хранятся порталом.

Сессия портала создаётся backend после успешного внешнего входа и защищается HttpOnly/Secure/SameSite cookie, CSRF-защитой и серверной проверкой авторизации каждого API. OAuth-secret и LDAP bind secret задаются через secrets менеджер окружения; они не попадают в frontend bundle, журналы или репозиторий. Портал не реализует свою 2FA.

### 3. Данные заявки, статусы и решения

Хранить `partner`, `external_identity`, `partner_application`, `application_revision`, `review_decision`, `consent_record` и `audit_event` раздельно. Заявка содержит тип партнёра, контактные данные, страну/регион, статус и результат tax-ID проверки. Повторная подача после отказа добавляет редакцию, а не переписывает исходные данные и решение. При одобрении создаётся или активируется партнёрская запись и привязывается менеджер; запись партнёра ссылается на внешнюю identity.

Решение менеджера выполняется транзакционно с проверкой текущего статуса, чтобы конкурентные одобрение и отказ не применились вместе. Решения и публикации контента записываются в append-only audit history с актором и временем. Контроллеры получают данные только через policy-scoped запросы партнёра; client-provided ID сам по себе не даёт доступ к чужой записи.

Для каждой заявки хранить locale, номер версии оферты и согласия на обработку персональных данных, timestamp и ссылку на неизменяемый опубликованный текст (либо его content hash). Новая редакция не меняет исторические согласия. ИНН/БИН хранить как чувствительные данные с защитой at-rest согласно ТЗ; уникальность и поиск реквизитов выполнять по отдельному защищённому индексу/хэшу, если это подтвердит security review.

### 4. Ручная проверка реквизитов

Каждая новая и повторно поданная заявка получает статус `MANUAL_REVIEW` и ожидает решения уполномоченного сотрудника независимо от синтаксической проверки введённых реквизитов. Вызовы налоговых реестров не выполняются в текущем этапе. Их возможное подключение потребует отдельного решения и не отменит ручное решение сотрудника без нового требования.

### 5. Back-office и API-контракты

Публичные API отвечают за получение опубликованной формы, OAuth-переход, создание/чтение собственной заявки и повторную подачу. Back-office API предоставляет очередь и карточку заявки, approve/reject, назначение менеджера, просмотр аудита, черновики локалей, import/export и публикацию. Примеры маршрутов: `GET /api/v1/public/registration-content/{locale}`, `GET /api/v1/auth/yandex/start`, `GET /api/v1/auth/yandex/callback`, `POST /api/v1/partner-applications`, `GET /api/v1/partner-applications/me`, `GET /api/v1/admin/partner-applications`, `POST /api/v1/admin/partner-applications/{id}/approve|reject`, `PUT /api/v1/admin/registration-content/{locale}/draft`, `POST /api/v1/admin/registration-content/{locale}/publish`.

Маршруты back-office ограничиваются серверными LDAP-derived ролями. Менеджер может модерировать заявки; системный администратор может настраивать локали, оферты и logo mapping. Ошибки имеют стабильный машинный код и локализованное безопасное описание; duplicate identity или tax-ID не должны раскрывать данные существующего партнёра.

### 6. Редактируемые переводы, версии оферты и брендинг

Хранить строки формы, тексты согласий, offer body и locale settings в versioned content store в PostgreSQL. UI-элементы администрирования позволяют редактировать каждый язык вручную, импортировать/экспортировать JSON/XLSX, просматривать draft и публиковать целый согласованный набор. Публикация не проходит при неполном наборе обязательных ключей или отсутствии offer/brand для локали. Автоматический перевод не подключать.

Выбранную локаль хранить в browser storage до регистрации, затем — в профиле партнёра. Логотип отображать по активной локали: SimbirSoft для RU/EN и 17Soft для KZ. Администратор настраивает связь локали с уже загруженным и утверждённым logo asset; произвольную загрузку изображения в этот change не включать. 17Soft asset пока отсутствует в проекте и требуется как входной материал для production.

Публичная регистрация включается в production только после публикации согласованных RU/KZ/EN текстов, отдельных юридически утверждённых оферт на каждом языке и утверждённых logo assets. Для чистой установки контент не сидируется из demo fixtures: системный администратор заполняет и публикует его через back-office. До настройки регистрация закрыта. Базовые подписи самой формы настройки остаются встроенной служебной локализацией, достаточной для её заполнения.

### 7. Пустой production и совместимость с текущим прототипом

Не переносить mock arrays из `src/data.js` в production. Demo fixtures разрешены только в явно включённом dev/demo окружении; реальные production-сессии всегда читают API. На этом change профиль показывает данные из записи регистрации, а не текущий профиль-образец; остальные модули кабинета до подключения их API отображают пустые состояния. Это исключает показ чужих или вымышленных сведений одобренному партнёру, не превращая этот change в реализацию всех бизнес-модулей портала.

### 8. Границы и проверки реализации

Backend реализуется в Spring Boot с миграциями PostgreSQL; frontend обновляется в существующем React/Vite SPA. Контракт API документируется в OpenAPI 3.0. Проверки включают unit/integration тесты регистрации и переходов состояний, provider callback с некорректным `state`, контролируемые тесты LDAP/role mapping, tests of mandatory manual-review routing, API authorization tests для доступа к чужим заявкам и end-to-end сценарии на RU/KZ/EN с различными логотипами. Тесты используют вымышленные данные и mock-провайдеры; production credentials не требуются для CI.

### 9. Контейнеризация и конфигурация секретов

Frontend, backend и необходимые инфраструктурные зависимости должны иметь воспроизводимый запуск через Docker; локальный и тестовый набор сервисов описывается Docker Compose. Контейнерные образы не содержат окруженческих секретов и могут продвигаться между окружениями без пересборки из-за credentials. Настройки интеграций читаются приложением из переменных окружения. Для локальной разработки `.env` исключён из Git; `.env.example` документирует названия и назначение параметров, не включая действующие значения. Для CI и production секреты подаются защищённым хранилищем/платформой в runtime. Секреты нельзя выводить в логи или передавать в публичную конфигурацию frontend.

## Risks / Trade-offs

- [Yandex ID требует регистрации OAuth-приложения и нужных разрешений] → включить создание приложения, callback URLs и хранение client secret в production-readiness checklist; использовать официальный API и минимум запрашиваемых данных.
- [Ручная проверка всех заявок увеличивает нагрузку на сотрудников] → показывать все новые заявки в очереди модерации; автоматизацию рассматривать отдельным изменением после согласования провайдеров и правил.
- [Отсутствие утверждённых оферт или логотипа 17Soft блокирует регистрацию] → проверять комплектность локали до публикации, показывать администратору конкретные отсутствующие материалы и не подменять их демо-текстом или чужим брендом.
- [LDAP-группы и структура directory зависят от окружения SimbirSoft] → роли сопоставлять конфигурацией и проверять в тестовом LDAP до production; при недоступности LDAP закрывать внутренние операции.
- [Сбой внешнего провайдера идентификации мешает входу партнёров] → не дублировать пароли в портале; явно показать временную ошибку входа и журналировать только безопасные идентификаторы запроса.
- [Пустые production-разделы отличаются от текущего demo-макета] → держать demo режим только вне production, а неподключённые разделы показывать с корректными пустыми состояниями.

## Migration Plan

1. Развернуть backend и PostgreSQL-схему через forward-only миграции. Реальных данных партнёров в прототипе нет; demo fixtures не мигрируются.
2. Настроить Yandex ID OAuth app, LDAP-группы/role mapping и конфигурацию для ручной проверки заявок.
3. Войти сотрудником-администратором через LDAP и внести через back-office тексты интерфейса, согласия, оферты и locale-to-logo mapping для RU/KZ/EN; опубликовать только юридически утверждённые редакции.
4. Включить регистрацию сначала на тестовом контуре и проверить весь lifecycle с тестовыми Yandex/LDAP identities; все заявки проходят ручную проверку.
5. Включить production feature flag только при готовности всех трёх локалей и официального 17Soft asset. До этого публичная регистрация остаётся выключенной.

Откат выполняется выключением feature flag и возвратом frontend к закрытому состоянию регистрации; схема и audit history сохраняются. Разрушительные down-migrations не выполнять. После создания реальных заявок откат не удаляет их, решения или сохранённые согласия.
