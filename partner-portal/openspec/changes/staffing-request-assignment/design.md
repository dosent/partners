# Design

## Context

Партнёрский API модуля `staffing` создаёт и показывает заявки только их владельцу. Доменная запись `StaffingRequest` хранит статус, требования и `@Version`, но не ответственного сотрудника; production-очереди пока нет. Роль `RESOURCE_MANAGER` уже получает permission `staffing.request.manage`. Модуль `access` публикует `StaffRoleLookup` для межмодульной проверки ролей, а модуль `audit` пока предоставляет application interface для аудита изменений профиля.

Целевая архитектура — модульный монолит. `staffing` владеет заявкой и своей транзакцией; контроллеры остаются тонкими; cross-module repository access запрещён. DDL добавляется только новой Liquibase-миграцией.

## Goals / Non-Goals

**Goals:**

- Дать уполномоченным сотрудникам одну очередь для просмотра краткого контекста заявок и их текущего ответственного.
- Назначать не более одного ответственного Resource Manager на заявку; разрешать переназначение и снятие назначения.
- Проверять роль назначаемого сотрудника на сервере через application interface `access`.
- Хранить текущего ответственного и неизменяемую историю назначений; атомарно сохранять её с изменением заявки.
- Сообщать о конкурентном изменении заявки через `409`.

**Non-Goals:**

- Смена статусов, фильтры SLA, запрос уточнений, уведомления и анализ исходного ТЗ.
- Назначение отдельных кандидатов, изменение ролей сотрудников или управление LDAP.
- Раскрытие партнёрам логина ответственного либо административного API.

## Decisions

### 1. Назначение принадлежит агрегату staffing-заявки

Добавить nullable `assignedResourceManagerUsername` в доменную модель и одноимённый nullable столбец `assigned_resource_manager_username` в `staffing_request`. Новые заявки создаются без назначения. Username нормализуется модулем `access`; внешний LDAP или таблицы grants напрямую из `staffing` не читаются. `@Version` агрегата защищает назначение от конкурентной записи.

В том же application transaction модуль `staffing` вызывает порт модуля `audit`. История append-only содержит заявку, тип события (`ASSIGNED`, `REASSIGNED`, `UNASSIGNED`), прежнего и нового ответственного, сотрудника-инициатора и время. Повторное назначение того же сотрудника не создаёт событие истории.

### 2. Staff API защищён отдельным permission

Добавить маршруты:

- `GET /api/v1/admin/staffing-requests?page=0&size=20` — постраничная очередь, отсортированная от новых заявок к старым. Строка очереди содержит ID, номер, название роли, количество специалистов, статус, дату создания, username ответственного (если задан) и `version` для optimistic locking.
- `GET /api/v1/admin/staffing-requests/assignees` — список username сотрудников с ролью `RESOURCE_MANAGER` для выбора ответственного.
- `PUT /api/v1/admin/staffing-requests/{requestId}/assignment` с `{ "username": "...", "expectedVersion": 0 }` — назначить или заменить ответственного. Значение `username: null` снимает назначение.

Security rules и application service требуют `staffing.request.manage`. `StaffRoleLookup` получает read-only метод для списка сотрудников с заданной внутренней ролью; список не раскрывает LDAP-атрибуты и включает только username и роль. Application service отклоняет неизвестный username или сотрудника без `RESOURCE_MANAGER` с `400`. Несуществующая заявка возвращает `404`, конкурентная версия — `409`. Изменяющие запросы сохраняют штатную CSRF-защиту.

Каждый запрос изменения передаёт `expectedVersion`, полученную из строки очереди. Несовпадение версии возвращает `409` до записи; проверка `@Version` дополнительно защищает от гонки между чтением и фиксацией.

Очередь возвращает только данные, необходимые для назначения. Детали контактов партнёра и вложения не входят в её DTO. Партнёрские маршруты и ответы остаются без изменений.

### 3. Страница использует существующую staff-навигацию

Добавить back-office страницу очереди, доступную при `staffing.request.manage`. В каждой строке сотрудник может выбрать Resource Manager, сохранить назначение или снять его; клиент передаёт версию строки вместе с изменением. После успешного изменения очередь обновляется, а ошибка отображается без потери выбора. Для отсутствия permission страница не загружает очередь; серверная проверка остаётся обязательной.

Интерфейс следует существующим компонентам и паттернам staff back-office. Подробную обработку заявки и смену статуса не добавлять.

### 4. Проверки

- Unit-тесты проверяют первичное назначение, переназначение, снятие, запрет не-Resource Manager и отсутствие лишнего события при повторе.
- Persistence/API тесты проверяют nullable поле, очередь, append-only историю, `404`, `400`, `409`, CSRF и запрет запросов без permission.
- Браузерный e2e проверяет создание staffing-заявки тестовым партнёром, назначение её сотрудником, переназначение/снятие и запрет доступа сотруднику без permission.

## Risks / Trade-offs

- Список Resource Manager основан на текущих RBAC grants; это соответствует принятой модели, в которой доступ сотрудников определяется приложением, а не LDAP-группами.
- В очереди показываются username, а не имена из LDAP: отдельный справочник сотрудников не входит в текущий интерфейс `access`.
- История назначения принадлежит модулю `audit`; вызов его application interface выполняется в транзакции staffing use case, чтобы изменение заявки не фиксировалось без записи истории.

## Migration Plan

Добавить nullable колонку через новую Liquibase-миграцию и таблицу истории назначений. Существующие заявки остаются без ответственного. Откат приложения совместим с добавленными nullable/новой таблицей; уже записанные события истории не преобразуются.
