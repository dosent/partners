# Design

## Context

Основание изменения — proposal.md; пользовательский контракт — specs/manual-candidate-catalog/spec.md. Это проект решения для согласования, а не описание уже реализованного поведения.

Архитектурная основа сверена с docs/superpowers/specs/2026-09-30-full-partner-portal-design.md, design общего изменения, staffing-request-assignment и partner-staffing-request-intake. React использует отдельные staff-страницы и слой API. Backend — модульный монолит с application interfaces; прямой доступ к чужим repositories запрещён. Права candidate.manage уже выдаются роли RESOURCE_MANAGER. candidate и finance пока содержат только package-info; демонстрационный пул в App.jsx доступен только в dev-демонстрации и не связан с PostgreSQL.

Документный модуль уже имеет ObjectStorage, MalwareScanner, LeadDocumentService.prepare и adapters для вложений заявок. Их переиспользование требует общей проверки документов без lead-специфичных сообщений об ошибке. Хранилище и антивирусные adapters заново не создаются.

В текущих StaffingRequest, CreateStaffingRequestRequest и форме заявки клиентская часовая ставка отсутствует. Для настоящего расчёта экономики позже потребуется отдельно согласовать её источник и хранение вместе с формулами. Этот этап сохраняет ставку кандидата; он не создаёт видимость готового расчёта.

## Goals / Non-Goals

**Goals:** сохранить ручные данные надёжно, применить существующий staff-доступ, разделить профили/ставки/файлы по владельцам модулей и создать проверяемый вертикальный поток.

**Non-Goals:** не создавать Jira adapter, сервис синхронизации, финансовый калькулятор, партнёрскую публикацию, механизм резервирования или назначения. Будущий импорт не требует инфраструктуры, не используемой первым этапом.

## Decisions

### 1. Первый этап — внутренний staff-каталог

Рекомендуется отдельная страница /staff/candidates в существующем StaffFrame, ссылка из кабинета сотрудника при candidate.manage. Экран включает заголовок и «Добавить кандидата», поиск, фильтр доступности, список и пагинацию. По умолчанию показаны доступные; пустое состояние не содержит тестовых профилей. Карточка показывает профиль, текущую ставку, время обновления, доступность и скачивание CV; редактирование использует те же поля.

Альтернативы: сразу реализовать партнёрский пул — это дополнительно требует правил обезличивания и подтверждения, которых пользователь сейчас не запрашивал; продолжить dev-прототип — он не обеспечивает сохранение, реальные права и общий список. Выбран рабочий внутренний каталог.

Форма: роль/направление, необязательный грейд, навыки, опыт в годах и месяцах, описание, CV, ставка кандидата за час, валюта и доступность с явным выбором. В API опыт передаётся общим числом месяцев. Внутренний уникальный код генерируется сервером; ФИО и контакты не являются обязательными полями. Файлы могут содержать персональные данные и остаются внутренними.

Используются ui.css и docs/ui-guidelines.md. Новые ключи интерфейса публикуются через localization; русские тексты в спецификации являются предложением для согласования. Утверждённые переводы не придумываются; KZ/EN вводятся людьми. До их публикации действует политика отсутствующей локали портала.

### 2. Владение данными соответствует существующей архитектуре

candidate владеет CandidateProfile: ID, уникальный код, роль, грейд, навыки, experienceMonths, description, availability, createdAt, updatedAt, createdBy, updatedBy, version. Доступность — AVAILABLE или UNAVAILABLE; выбранное состояние обязательно. Это ручное сведение, не вычисление занятости.

finance владеет CandidateHourlyRate: candidateId, amount NUMERIC(12,2), currency, changedAt, changedBy и собственной версией. Денежные значения представлены BigDecimal, в JSON — десятичной строкой; binary floating point для хранения и расчётов не используется. Валюта проверяется как ISO 4217, сумма положительна и имеет максимум два дробных знака. Finance публикует application interface сохранения и пакетного чтения ставок. Он не обращается к repository кандидатов; candidate вызывает его только после своей проверки профиля и прав. Ставка не трактуется как выручка или итоговая себестоимость с налогами.

document владеет CV: ID файла, candidateId, версия, имя, MIME, размер, checksum, objectKey, статус проверки, создатель и время. candidate вызывает порт хранения CV, реализованный document. Скачивание сначала проверяет профиль и candidate.manage, затем обращается к application interface document. Партнёрский endpoint в этом этапе не добавляется.

Альтернатива хранения суммы прямо в candidate проще локально, но расходится с архитектурным владельцем ставок finance. Отдельный микросервис не нужен. Выбраны application interfaces внутри существующего монолита и общий transaction manager.

### 3. Одна транзакция профиля и ставки, компенсация файлов

Application service candidate владеет транзакцией создания/изменения. Finance и document участвуют в ней через общий DataSource/transaction manager; отдельной REQUIRES_NEW транзакции нет. На каждый апдейт профиля, ставки или CV проверяется expectedVersion кандидата и повышается общая версия профиля. JPA @Version также защищает от гонки после чтения.

Создание принимает профиль, ставку и обязательный CV одной multipart-операцией. До записи БД проверяются поля и файл. После успешного сканирования CV кладётся в S3 под новым ключом; метаданные, профиль и ставка фиксируются атомарно. Ошибка S3 не создаёт профиль; rollback БД удаляет новый объект компенсирующим действием. Повтор операции с тем же Idempotency-Key и тем же содержимым возвращает созданного кандидата; иное содержимое с тем же ключом возвращает конфликт. Ключ формируется существующим совместимым с HTTP-стендом генератором UUID и сохраняется в браузере до завершения операции.

Замена CV проверяет актуальную версию и файл, сохраняет новый объект под новым ключом и переключает ссылку транзакционно; старый текущий файл остаётся до commit. Предыдущие версии метаданных и файлов сохраняются как внутренние версии; маршрут скачивания выдаёт текущую проверенную версию. Неудачная замена оставляет прежний CV и профиль. Отсутствующий из-за сбоя повторный файл браузер предлагает выбрать заново, не очищая текст формы.

### 4. REST API и контроль доступа

Все маршруты требуют активную staff-сессию и candidate.manage; изменяющие запросы сохраняют существующую CSRF-защиту. Проверки выполняются в security и application слоях, а не только в React.

- GET /api/v1/admin/candidates?q=&availability=AVAILABLE&page=0&size=20 — список с текущими ставками; size ограничен 100, page неотрицательный, q не более 200 символов.
- GET /api/v1/admin/candidates/{id} — карточка, текущая ставка, сведения о CV и version.
- POST /api/v1/admin/candidates — multipart: JSON-поле profile с описанием, опытом, доступностью и hourlyRate; поле cv; обязательный Idempotency-Key.
- PUT /api/v1/admin/candidates/{id} — JSON с изменяемыми полями, hourlyRate и expectedVersion; без замены CV.
- PUT /api/v1/admin/candidates/{id}/cv — multipart с файлом и expectedVersion; возвращает новую версию карточки.
- GET /api/v1/admin/candidates/{id}/cv — текущий файл, Content-Disposition attachment; без публичного objectKey или постоянного URL.

Создание возвращает 201, успешное чтение/изменение 200; повтор успешно созданной операции возвращает ту же карточку. Ошибки используют единый формат code/message/traceId/fieldErrors: 400 для полей, 401/403 для сессии/прав, 404 для отсутствующей карточки, 409 для версии или идемпотентности, 413 для превышения размера, 422 для отклонённого сканером файла и 503 при недоступном хранилище/сканере. Multipart-ограничения конфигурируются согласованно с 20 МБ и накладными расходами запроса. Контроллеры и records документируются SpringDoc.

Поиск выполняется сервером, регистронезависимым буквальным вхождением: спецсимволы SQL не становятся шаблонами пользователя. Устойчивая сортировка updatedAt DESC, id DESC. Ставки для страницы получаются одним пакетным обращением к finance, без N+1. Простые выборки реализуются JPA; если нужен специализированный SQL, он размещается в resources/sql/candidate и вызывается принятым QueryHelper.

### 5. Согласованность с будущими этапами

Ручные записи не получают фиктивных Jira ID и не запускают внешние обращения. При подключении Jira отдельно согласуются источник истины, стабильный внешний ID, период синхронизации, разрешение конфликтов ручных изменений и трактовка ставок. Импорт пойдёт через application interfaces, а не прямую запись в таблицы.

Финансовые формулы пользователь предоставит отдельно. До их согласования нет вычисления разницы ставок, процентов, конвертации, налогов, рабочих часов или итоговой эффективности. Клиентская ставка и ставка кандидата — разные исходные данные; отсутствие первой не заменяется нулём. Отдельное изменение экономики должно определить клиентскую ставку по заявке, валюту, период действия и трактовку обеих ставок.

## Risks / Trade-offs

- [Ручная доступность устаревает] → показывать время изменения; не называть её проверкой загрузки или подтверждением Production.
- [CV содержит персональные данные] → staff-доступ, проверка каждой выдачи; никакой публикации партнёрам в этом этапе.
- [S3 и PostgreSQL не имеют общей транзакции] → уникальные ключи, rollback cleanup, сохранение прежней версии до успешной фиксации и тесты с отказами.
- [Ставки конфиденциальны] → отдельные staff DTO и серверное permission; отсутствие сумм и CV в журналах, trace и сообщениях ошибок.
- [Локали не подготовлены] → использовать существующий модуль ручного управления текстами и его политику отсутствующей локали.
- [В модели заявки отсутствует клиентская ставка] → не считать экономику; согласовать источник отдельно вместе с формулами.

## Migration Plan

1. После одобрения спецификации добавить новые additive Liquibase changeset для профилей, ставок и CV; существующие заявки и данные не преобразовывать.
2. Создать уникальные ограничения для кода, идемпотентного ключа и единственной текущей ставки на candidateId; добавить version и индексы пагинации/доступности. Проверить чистую и существующую PostgreSQL.
3. Подключить защищённые API и staff-раздел после готовности серверного хранения; не добавлять production seed-данные.
4. При откате приложения новые таблицы и файлы сохраняются; удаляющие миграции не выполняются.

## Verification

Domain/application: поля, нулевой опыт, нормализация навыков, сумма/валюта, доступность, атомарность, идемпотентность и конфликты. PostgreSQL: JPA mapping, версии, пагинация, finance/candidate/document в одной транзакции. MockMvc: RBAC, CSRF, multipart и ошибки. Document tests: тип, размер, сканирование, замена, отказы S3 и rollback cleanup. ArchUnit: отсутствие доступа к чужим repositories.

Обязательный e2e в отдельном Docker Compose с реальными backend/PostgreSQL: Resource Manager создаёт кандидата с вымышленным CV и ставкой, перезагружает страницу, ищет, редактирует, меняет доступность и скачивает/заменяет CV; отдельные сценарии проверяют отказ без прав и конфликт двух вкладок. Формы дополнительно проверяются в Chromium/WebKit, на утверждённых ширинах и фактическом масштабе 125%. Перед интеграцией требуются frontend build, применимые тесты, OpenSpec validation и успешный e2e. Этот документ не утверждает, что реализация или её проверки уже выполнены.
