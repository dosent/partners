## Контекст и текущая архитектура

В `src/App.jsx` раздел «Мои лиды» сейчас находится в демонстрационной оболочке: состояние хранится в React, исходные записи заданы в `src/data.js`, а форма не отправляет данные на сервер. Backend-модуль `lead` пока содержит только каркас пакетов. Поэтому production-доска требует полноценного вертикального сценария, а не только замены таблицы на визуальные колонки.

Сохраняются действующие границы проекта: React/Vite, Spring Boot 3 и Java 21, REST `/api/v1`, модульный монолит, PostgreSQL, Liquibase, файловое хранилище через существующий модуль `document`. Frontend получает серверное состояние через принятый в кабинете data-access слой. Контроллер не реализует бизнес-логику. Проверка партнёра и владельца выполняется на сервере в application/security policy.

## Решения

### Партнёрская доска

На desktop доска показывает горизонтальные колонки и прокручивается по горизонтали при нехватке ширины. На узком экране показывается одна выбранная колонка с переключателем этапа; ширина карточек не выходит за экран. Порядок колонок:

1. «Новый» — `NEW`.
2. «Квалификация» — `QUALIFICATION`.
3. «Проверка совпадения» — `DUPLICATE_REVIEW`.
4. «В работе» — `IN_WORK`.
5. «Успешно» — `WON`.
6. «Закрыт» — `LOST` и `REJECTED`; исходный статус остаётся видимым на карточке и в деталях.

Карточка показывает номер, компанию, краткий запрос, бюджет (если передан), точный партнёрский статус, дату обновления и назначенного менеджера, если он доступен партнёру. Количество в заголовке колонки соответствует текущему отфильтрованному результату. Поиск выполняется по компании, запросу и домену/ИНН самого лида; фильтры — статус и период обновления. Партнёр не может менять этап, назначенного менеджера или данные после создания. В частности, drag-and-drop статуса отсутствует.

Кнопка создания сохраняет существующие поля формы: компания, домен или ИНН, запрос, бюджет/валюта, предполагаемый старт, контактное лицо, email, описание и PDF/DOCX до 20 МБ. Успех подтверждается сервером и возвращает созданный лид. Ошибка сохраняет введённые значения и доступно объясняется пользователю.

Выбор карточки открывает страницу/панель деталей с собственными реквизитами лида, статусом и историей, партнёрскими комментариями, ответами и доступными вложениями. Внутренние заметки, сведения о чужом лиде и детали совпадения не попадают в DTO партнёра. Возможное совпадение обозначается нейтральным статусом ручной проверки.

### API и безопасность

API партнёрского модуля предоставляет постраничную выдачу лидов текущего партнёра с параметрами поиска, статуса и периода, создание лида и чтение деталей по ID. Точные URI и DTO фиксируются при реализации после сверки с текущими соглашениями API; все операции находятся под `/api/v1`. Tenant/owner scope берётся только из аутентифицированного principal, а не из query/body. Недоступный или чужой ID не раскрывает существование записи. Выдаваемые DTO являются партнёрскими проекциями; сообщения помечаются видимостью и исключают внутренние заметки.

История статусов доступна только для чтения; критические переходы выполняет back-office use case с проверкой допустимости и optimistic locking. Вложения проходят серверную проверку типа и размера и выдаются через проверку доступа модуля `document`.

### Состояния и доступность

Доска поддерживает загрузку, ошибку с повтором, пустой список с действием «Добавить лид», отсутствие результатов поиска/фильтров с их сбросом. Клавиатурное управление, семантические кнопки, видимый фокус, текстовые подписи статусов и корректное чтение screen reader обязательны. Цвет не является единственным обозначением статуса.

Демо-данные разрешены только в `/demo`/E2E. Production доска не подставляет их при пустом ответе или ошибке API.

## Проверки

- Domain/application: переходы статусов, создание и область партнёра.
- API/security: выдача собственных записей, отказ в раскрытии чужих ID и внутренних комментариев, валидация формы/файлов.
- Browser E2E: создание и появление лида в `NEW`, поиск/фильтрация и просмотр карточки; отказ/пустое состояние и межпартнёрская изоляция.
- Responsive E2E/visual checks: desktop-доска и мобильное переключение колонок без обрезанного содержимого.

## Контракт чтения и переписки

Минимальный REST-контракт (все маршруты под `/api/v1`, principal определяет партнёра):

- `GET /partner/leads/board?query=&updatedFrom=&updatedTo=&status=&limitPerColumn=&cursor.<lane>=` — возвращает шесть lane-представлений; у каждого есть `total`, `items`, `nextCursor`. Период фильтрует по `updatedAt` включительно, передаётся в UTC. Карточки упорядочены `updatedAt DESC, id DESC`. `status` опционально ограничивает результат одной lane.
- `POST /partner/leads` — создаёт лид. Текстовые поля: `companyName`, `domainOrTaxId`, `requestSummary`, `budgetAmount`, `budgetCurrency`, `plannedStartAt`, `decisionMakerName`, `decisionMakerEmail`, `description`; файл загружается в рамках согласованного существующего file-upload потока. Серверный статус при создании `NEW`.
- `GET /partner/leads/{leadId}` — возвращает только партнёрскую проекцию, историю и сообщения, видимые партнёру.
- `POST /partner/leads/{leadId}/messages` — добавляет сообщение сторон в собственный лид; внутренний тип комментария недоступен партнёру.

Все DTO — отдельные API records, не JPA entity. Чужие/несуществующие ID дают одинаковый безопасный ответ. Числа карточек — totals после поиска/периода; пагинация независима по lane. Повторная загрузка следующей страницы использует lane cursor. Изменение фильтра инвалидирует курсоры и загружает первую порцию каждой колонки.

## Уточнение по файлам

Файл допускается только при совпадении allow-list расширения `.pdf`/`.docx` и соответствующего MIME-типа, размере не более 20 МБ, безопасном имени и успешном завершении проверки. Метаданные, checksum, владелец и статус проверки хранятся в модуле `document`; файл в pending/quarantined/failed состоянии недоступен для скачивания. Прямой доступ к object storage из frontend запрещён.
