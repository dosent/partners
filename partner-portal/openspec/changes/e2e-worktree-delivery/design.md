# Design

## Context

Frontend работает на React/Vite, backend — на Spring Boot и PostgreSQL. Сейчас в проекте есть unit-, API- и архитектурные проверки, но нет браузерной e2e-инфраструктуры. Yandex ID и LDAP являются внешними зависимостями; текущая бизнес-логика регистрации и RBAC должна оставаться неизменной. Требования заданы в `specs/e2e-delivery/spec.md` и `specs/platform-quality-security/spec.md`.

## Goals / Non-Goals

**Цели:** воспроизводимый e2e-запуск локально и в CI, изолированная тестовая аутентификация, обязательный контроль интеграции через feature worktree.

**Вне рамок:** изменение правил регистрации, модерации или RBAC; проверка реальных внешних аккаунтов; автоматический push.

## Decisions

1. **Браузер и реальные внутренние сервисы.** Playwright будет управлять собранным frontend, а backend и PostgreSQL будут работать в отдельном Compose-проекте. Это проверяет фактическую связку UI, API и persistence; MockMvc и unit-тесты не могут подтвердить этот путь. Для диагностики сохраняются HTML-отчёт, trace, скриншоты при ошибке и журналы Compose.
2. **Отдельный e2e-артефакт аутентификации.** Тестовые адаптеры Yandex ID/LDAP размещаются в отдельном backend source set и включаются только явным e2e-профилем. Обычный `bootJar` проверяется на отсутствие тестовых классов. Альтернатива — общий артефакт с условным профилем — оставляет тестовый вход доступным в production-образе, поэтому не принимается. Искусственный OAuth-код подменяет только внешнего поставщика; callback/state, CSRF, permissions, application services и БД остаются настоящими.
3. **Данные и жизненный цикл.** Тесты создают уникальные вымышленные идентификаторы, а отдельный Compose project и том PostgreSQL удаляются после прогона. Подготовка юридического тестового контента идёт через штатный staff API с CSRF; реальный утверждённый контент и production credentials не используются. Обычный Compose-проект разработчика не затрагивается.
4. **Git gate и CI.** Команды запуска e2e публикуются в `package.json` и README. GitLab CI вызывает полный `npm run test:e2e` для feature-веток и `main`, сохраняет отчёты при любом исходе. Локальный порядок: worktree от актуальной `main` → изменения и применимые проверки → полный обязательный e2e → коммит feature-ветки → интеграционный коммит в `main`. Ошибка e2e возвращает работу в feature worktree. Push выполняется отдельно.

## Risks / Trade-offs

- Ошибка тестовой изоляции может открыть обход аутентификации в обычной сборке → отдельный source set и проверка состава обоих артефактов.
- Нестабильность e2e из-за общего состояния → отдельная БД, уникальные данные и один worker на первом этапе.
- Недостаточная диагностика CI замедлит исправление → сохранять trace, скриншоты, HTML-отчёт и очищенные от секретов журналы сервисов до остановки Compose.

## Migration Plan

Сначала добавить изолированное окружение и smoke, затем сценарии текущих потоков, после чего сделать полный набор обязательным в CI. Интеграция в `main` выполняется лишь после прохождения полного набора. Откат выполняется обратным коммитом тестовой инфраструктуры; схема production-БД и бизнес-данные не меняются.
