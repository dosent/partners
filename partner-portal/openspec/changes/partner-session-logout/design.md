# Design

## Context

Партнёрский Yandex ID flow и сессия уже принадлежат модулю `access`. `YandexAuthController` предоставляет начало OAuth-потока и чтение сессии; отдельного выхода партнёра пока нет. Выход сотрудника уже реализован POST-запросом с инвалидированием HTTP-сессии и очисткой `SecurityContext`. Frontend использует cookie-сессии, общий helper получения CSRF-заголовков в `partnerRegistrationApi.js`, а одобренный кабинет выводит верхнюю шапку в `ApprovedPartnerPortal`.

## Goals / Non-Goals

**Goals:**

- Следовать имеющейся модели cookie-сессий и защите CSRF.
- Завершать сессию на сервере до показа публичного состояния.
- Сделать выход доступным с клавиатуры и на узком экране в правой части шапки кабинета.

**Non-Goals:**

- Выход из Yandex ID или отзыв токена у провайдера.
- Изменение входа, регистрации, роли или времени жизни сессии.
- Добавление выхода для демонстрационного прототипа или сотрудников.

## Decisions

### Endpoint в существующем Yandex auth controller

Добавить `POST /api/v1/auth/yandex/logout` в `YandexAuthController`, так как endpoint управляет той же web-сессией, что и текущая Yandex-аутентификация. Операция инвалидирует существующую HTTP-сессию при её наличии и очищает `SecurityContext`. Маршрут должен требовать роль партнёра и сохранять штатную CSRF-защиту. Это соответствует существующему staff logout и не создаёт второй механизм управления сессиями.

Альтернатива — универсальный logout endpoint Spring Security — не выбрана: стандартный logout сейчас явно отключён в `SecurityConfiguration`, а включение его изменило бы общую политику для обоих типов аккаунтов.

### Frontend обрабатывает выход как явное действие

Добавить API-функцию выхода, получающую CSRF заголовок общим helper-ом. Кнопка в правой части `approved-portal-header` блокируется на время запроса, чтобы предотвратить повторные клики. После успешного ответа перейти на `/`; обработка маршрута повторно проверит отсутствие сессии и покажет публичный лендинг. При отказе показать сообщение в `role="alert"`, не очищать локальное отображение кабинета и дать пользователю повторить попытку.

Локальные заголовки и шапка используют уже загружаемый опубликованный контент; в этой небольшой функции текст кнопки и ошибки остаются текущими русскоязычными строками компонента, без изменения административного каталога переводов.

### Проверки

Backend проверяется тестами контракта/безопасности endpoint (валидный CSRF, invalidation, запрет неавторизованного доступа). Браузерный e2e проходит вход синтетического одобренного партнёра, нажимает выход, проверяет публичную страницу и подтверждает, что защищённая partner-session больше не доступна. Отказ выхода отдельно проверяется на frontend уровне.

## Risks / Trade-offs

- **Потеря сети после фактического invalidation, но до получения ответа** → интерфейс покажет ошибку и останется в кабинете до навигации/повтора; защищённые запросы всё равно будут отклонены сервером, а обновление страницы покажет публичное состояние.
- **CSRF-токен отсутствует из-за сбоя получения** → запрос не считается успешным; ошибка показывается, кабинет остаётся на экране.

## Migration Plan

Изменение не требует миграции данных. После развёртывания старые активные сессии сохраняют текущее поведение; новая операция становится доступна после обновления frontend и backend. Откат версии приложения убирает кнопку и маршрут без преобразования данных.
