# Design

## Context

См. `proposal.md` — Why. В рабочем кабинете уже есть место для раздела «Заявки на специалистов», но текущая форма находится только в dev-демо и сохраняет записи в состоянии React. Production-портал после одобрения профиля пока показывает пустые разделы. Backend уже содержит модульные пакеты `staffing`, `lead`, `document` и `localization`, но доменная модель заявок на специалистов ещё не реализована.

Существующие решения требуют React/Vite, Java 21 / Spring Boot 3, PostgreSQL, REST `/api/v1`, Liquibase и модульный монолит со слоями `api`, `application`, `domain`, `infrastructure`. Владение и права проверяются на сервере; партнёрские запросы используют существующую сессию и CSRF-механизм.

## Goals / Non-Goals

**Goals:**

- Встроить форму и список в рабочий кабинет, не опираясь на демонстрационные данные.
- Сохранить заявку и требования как доменную запись модуля `staffing`.
- Собирать только сведения, нужные для старта подбора; унаследованные и процессные значения не дублировать.
- Обеспечить серверную проверку владельца проекта/лида и файлов.

**Non-Goals:**

- Реализовывать всю очередь Production, назначение Resource Manager, SLA и анализ ТЗ: эти функции остаются в `staffing-request-management`.
- Создавать отдельный каталог проектов или заявку без доступного партнёру лида.
- Собирать фактические даты собеседований/выхода, внутренние комментарии и назначения.
- Создавать или изменять демонстрационные бизнес-записи для production.

## Decisions

### 1. Раздел кабинета с группированной одностраничной формой

Раздел содержит список заявок и действие создания. Форма остаётся на одной странице и разбивается на группы: «Проект», «Специалист», «Задачи и требования», «Условия и отбор». Уровень языка раскрывается только при включённом языковом требовании. Это сохраняет обзор всего запроса и не требует отдельной логики мастера/черновиков.

Альтернатива — пошаговый wizard — отклонена: для первой версии он усложнит навигацию и восстановление состояния без дополнительной ценности. Длинная неразделённая форма отклонена из-за низкой читаемости.

### 2. Сервер — источник истины для принадлежности

`staffing` владеет заявкой и вызывает публичный application interface `lead` для проверки доступности выбранного лида. В первой версии лид является единственным типом связи; отдельного project-модуля в кодовой базе нет. Владельца нельзя передать в DTO: сервер берёт его из текущей сессии. API предоставляет создание, постраничный список и detail только для владельца под `/api/v1/partner/staffing-requests`. Повтор запроса на создание должен поддерживать ключ идемпотентности.

Это сохраняет границы модулей и не даёт доступ к repository/entity `lead`. Прямая проверка связи на frontend не считается авторизацией.

### 3. Данные заявки принадлежат модулю staffing

Агрегат включает идентификатор владельца, ссылку на ровно один lead/project, роль, количество, грейд, обязательные и желательные навыки, описание задач, загрузку, формат/локацию, дату или признак неопределённого срока, языковые требования, процессные ответы и статус. Изменяемый агрегат использует `@Version`; создание и статус `NEW` фиксируются одной транзакцией. DDL вносится новой Liquibase-миграцией.

Альтернатива — хранить заявку как свободный текст лида — отклонена: теряются проверяемые требования, фильтрация и дальнейшая обработка Production.

### 4. Файлы проходят через document

В `staffing` сохраняются только ссылки на метаданные вложений. Тип/размер проверяются до сохранения; файл проходит существующий document-поток хранения и проверки. Если инфраструктура загрузки не доступна в момент создания заявки, форма сохраняет текстовую заявку без файлов и сообщает о неудачной загрузке отдельно.

### 5. Локализуемые строки управляются localization

Новые строки оформляются ключами и доступны на RU/KZ/EN только после ручной публикации. Не добавлять машинный fallback или неподтверждённый перевод. Эта функция не публикует форму в локали с отсутствующим обязательным набором строк.

### 6. Идентификатор операции совместим с HTTP-стендом

Клиент создаёт UUID v4 для идемпотентной операции из 16 криптографически случайных байтов через `crypto.getRandomValues`, доступный и на HTTP-стенде. Зависимость от `crypto.randomUUID`, отсутствующего вне secure context, не допускается. Ключ сохраняется при повторной отправке той же формы и обновляется при начале новой заявки; серверный контракт UUID остаётся прежним.

## Risks / Trade-offs

- [В активной полной спецификации ещё нет опубликованного каталога staffing-спецификации] → новый capability описывает только приём партнёрской заявки; очередь и SLA остаются в существующем change.
- [Документы могут быть недоступны раньше чем запись заявки] → текстовая заявка должна успешно сохраняться независимо, а ошибка вложения показывается отдельно.
- [Лиды могут не иметь всех Jira-метаданных] → отсутствующие внутренние атрибуты не блокируют создание и не запрашиваются повторно без отдельного требования.
- [Неопубликованный перевод может сделать локаль неполной] → раздел открывается только при полном наборе переведённых строк.

## Migration Plan

1. Добавить таблицы и ограничения новой Liquibase-миграцией; предыдущие changeset не менять.
2. Развернуть backend API и фронтенд раздела вместе с опубликованными строками RU/KZ/EN.
3. После миграции старые dev-демо записи не переносить; production-список изначально пустой.
4. При откате отключить маршрут и API; новые записи сохранять в базе и не удалять автоматической обратной миграцией.
