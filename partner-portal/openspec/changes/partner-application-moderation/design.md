## Цель и границы

Завершить серверную часть ручной модерации регистрационных заявок: уполномоченный сотрудник получает очередь, читает карточку и принимает решение. В том же изменении реализуется внутренняя RBAC, staff login UI, страница ожидания прав для LDAP-пользователей без ролей и экран выдачи ролей системным администратором. UI очереди back-office и публичный API регистрации остаются последующими этапами. Все новые и повторно поданные заявки остаются в `MANUAL_REVIEW`; налоговые реестры не подключаются.

## Архитектурный контекст

Приложение — модульный монолит. Модуль `access` отвечает за LDAP-аутентификацию, внутренние назначения сотрудников и RBAC. Модуль `partner` владеет заявками, решениями и их persistence. Сейчас права staff берутся из LDAP-групп, сущности/таблицы назначений нет, а API очереди и решений отсутствует. У заявки уже есть append-only история статусов, и JPA record использует `@Version`. Редакции заявки зашифрованы; очередь не должна читать или расшифровывать payload.

## LDAP-аутентификация сотрудников

LDAP используется только для проверки пользовательского пароля. Настройки deployment:

```text
LDAP_URL=ldaps://freeipa01.simbirsoft:636/
LDAP_USERS_DN=cn=users,cn=accounts,dc=simbirsoft,dc=dev
LDAP_CA_CERT_FILE=/app/certs/simbirsoft-ca.crt
```

DN сотрудника строится из экранированного `uid` и `LDAP_USERS_DN`. TLS соединение SHALL доверять CA из `LDAP_CA_CERT_FILE` и закрываться с ошибкой, если файл недоступен или сертификат сервера не проходит проверку; insecure fallback запрещён. В Compose сертификат предоставляется deployment-ом как read-only mount по указанному пути; сам cert не включается в Git или Docker image. Успешный LDAP bind подтверждает личность, но LDAP-группы не назначают роли приложения. Сотруднику без app-роли создаётся ограниченная сессия без business permissions.

## Внутренняя RBAC

Модуль `access` хранит назначения `username -> roles` в PostgreSQL. Набор ролей: `PARTNER_MANAGER`, `RESOURCE_MANAGER`, `FINANCE_CONTROLLER`, `SYSTEM_ADMIN`. Permission matrix определена в приложении и не редактируется LDAP-группами:

| Роль | Permissions в текущей матрице |
|---|---|
| `PARTNER_MANAGER` | `partner.application.read`, `partner.application.decide`, `lead.manage` |
| `RESOURCE_MANAGER` | `staffing.request.manage`, `candidate.manage` |
| `FINANCE_CONTROLLER` | `finance.manage` |
| `SYSTEM_ADMIN` | `staff.access.manage`, `partner.application.read`, `partner.application.decide`, `localization.manage`, `directory.manage` |

Только обладатель `staff.access.manage` может читать/назначать/отзывать роли сотрудника через `/api/v1/admin/staff-access/users/{username}/roles`. API принимает только известные enum роли, никогда не принимает произвольные permissions. Изменения назначения записываются в отдельный append-only журнал доступа с актёром и временем. Изменённая RBAC применяется к следующему запросу, даже если LDAP-сессия уже открыта; проверка доступа получает актуальные назначения из БД.

Liquibase создаёт bootstrap grant `ivan.neshin -> SYSTEM_ADMIN`. Это не локальная учётная запись и не обход LDAP: для получения сессии `ivan.neshin` обязан пройти LDAPS. Bootstrap grant нельзя снять или заменить через RBAC API, чтобы не потерять владельца первичных прав. После установки пользователь `ivan.neshin` может выдать `SYSTEM_ADMIN` другим сотрудникам.

Пользователь без выданной в приложении роли после успешной LDAP-аутентификации получает сессию `ACCESS_PENDING`: доступны только `GET /api/v1/auth/staff/session` и `POST /api/v1/auth/staff/logout`; business/admin API закрыты. SPA показывает просьбу обратиться к системному администратору и кнопку повторной проверки. После назначения роли повторный запрос `/session` возвращает актуальные permissions, и SPA открывает доступную часть back-office. Сотрудник, которому назначают роль, идентифицируется нормализованным LDAP username; наличие доступа к порталу всё равно требует успешного bind для этого username. Назначение ответственного менеджера при одобрении проверяется по текущему RBAC grant `PARTNER_MANAGER` через application interface модуля `access`, не через LDAP группу.

## Модерация заявок

В модуле `partner` реализуется API-first срез:

- `GET /api/v1/admin/partner-applications` возвращает только `MANUAL_REVIEW`, с пагинацией и стабильной сортировкой по времени подачи (старые первыми), затем по UUID. DTO списка содержит UUID, время подачи и номер последней редакции, без реквизитов и данных из зашифрованного payload.
- `GET /api/v1/admin/partner-applications/{id}` возвращает текущую редакцию, данные для рассмотрения, locale/версии согласий и неизменяемую историю статусов. Payload расшифровывается только для авторизованной карточки.
- `GET /api/v1/partner-applications/me` возвращает владельцу только статус собственной заявки и причину последнего решения; поиск идёт по authenticated provider/subject, чужой ID не принимается.
- `POST /api/v1/admin/partner-applications/{id}/approve`, `/reject` и `/request-changes` выполняют переход из `MANUAL_REVIEW`. Для последних двух требуется причина после trim длиной 1–1000 символов; управляющие символы отклоняются, реквизиты нельзя помещать в это сообщение.
- Решение и необязательное `assignedManagerUsername` сохраняются атомарно. Назначаемый пользователь должен иметь внутреннюю роль `PARTNER_MANAGER`.

Контроллеры принимают только валидируемые Java record DTO с OpenAPI-аннотациями и вызывают application service. `partner` может зависеть только от application interface модуля `access`, а не от его repository/JPA entity. Новая запись должна проходить через сервис модерации, владеющий транзакцией.

## Staff access UI

Staff login page отправляет credentials через CSRF-защищённый `/api/v1/auth/staff/login`. Успешный LDAP login без ролей возвращает `200` с `accessState=ACCESS_PENDING`, username и пустым roles list, сохраняя аутентифицированную ограниченную сессию. Только staff session endpoint и `POST /api/v1/auth/staff/logout` разрешены в этом состоянии; остальные защищённые маршруты возвращают `403`. Страница сообщает пользователю попросить администратора портала выдать роль и предоставляет кнопку повторной проверки через `GET /api/v1/auth/staff/session`. Когда администратор выдаёт роль, следующая проверка возвращает `accessState=ACTIVE` и актуальные роли, frontend открывает доступную часть back-office.

В back-office добавить экран управления доступом, доступный только с permission `staff.access.manage`: поле username, просмотр текущих ролей, форма изменения ролей из поддерживаемого enum и сохранение через `PUT /api/v1/admin/staff-access/users/{username}/roles`. Системный администратор может выдавать сотрудникам одну или несколько ролей. Очередь заявок и другие бизнес-разделы этим UI не добавляются.

## Конкурентные решения и ошибки

Решение допустимо только пока заявка имеет статус `MANUAL_REVIEW`. Сохранение использует `@Version` и transactional read-modify-save; проигравшая гонка или повторное решение даёт единый `409 CONCURRENT_MODIFICATION` и не добавляет статусное событие. Несуществующая заявка даёт `404`, недостаточная permission — `403`, неверные поля или переход — `400` в едином безопасном error envelope с `traceId`. Реквизиты, CA и пароли не записываются в логи.

## Данные и миграции

Не менять применённые changesets. Добавить отдельные миграции для таблиц назначения staff-role, append-only истории грантов и bootstrap grant `ivan.neshin`; отдельный changeset добавит nullable `assigned_manager_username` к partner application. Выборка очереди идёт через `QueryHelper` и зарегистрированный SQL в `resources/sql/partner/`, не выбирая `encrypted_payload`. Миграция не создаёт других пользователей или тестовых бизнес-записей.

## Проверка

Покрыть тестами LDAPS bind с переданным CA, отказ при недоступном/недоверенном CA, bootstrap grant только после LDAP, ограниченную сессию без ролей, выдачу/отзыв ролей и аудит, немедленное применение RBAC в уже открытой сессии, route permission matrix, UI-переход pending→active, owner scope, безопасный список, причины, назначение менеджера и гонку двух решений с одним успехом. Проверить миграции на чистой и предыдущей поддерживаемой схеме, OpenAPI и ArchUnit boundary.

## Ограничения этапа

Публичного API создания/повторной подачи заявки и UI очереди модерации сейчас нет. Этот этап реализует серверную поверхность модерации над существующим сохранённым агрегатом; реальная очередь заполнится после подключения публичной регистрации. Существующий Yandex callback нужен для регистрации и не блокируется статусом заявки. После появления API кабинета отдельный этап должен разрешать бизнес-доступ только заявкам со статусом `APPROVED`; этот этап такого кабинета не активирует. Frontend ограничен страницей состояния staff-доступа и экраном выдачи ролей.
