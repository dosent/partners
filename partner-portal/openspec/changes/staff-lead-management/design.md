## Context

Модуль `lead` уже хранит лиды, историю статусов и комментарии. `AdminLeadController` поддерживает только смену статуса, а `SecurityConfiguration` закрывает `/api/v1/admin/leads/**` разрешением `lead.manage`. В кабинете сотрудника есть отдельные страницы модерации и управления доступом с общим `StaffFrame`.

## Goals / Non-Goals

**Goals:** дать сотруднику с `lead.manage` очередь и карточку лида; сохранить комментарии с разделением видимости; использовать серверную проверку статусов и прав.

**Non-Goals:** менять вход LDAP, партнёрскую Kanban-доску, схему назначения ответственных, систему уведомлений и политику выдачи вложений.

## Decisions

1. Расширить существующий administrative API: постраничная очередь с поиском/фильтром, детали лида и добавление сообщения с признаком `internal`.
2. Реализовать чтение и запись через application service и `LeadStore`; JPA-запросы остаются внутри модуля `lead`. Новый Liquibase changeset добавляет nullable `author_name` к сообщениям, чтобы сохранять логин сотрудника без изменения старых записей.
3. Добавить `/staff/leads` в существующую маршрутизацию и ссылку на него в кабинете только для сессий с `lead.manage`. UI показывает разрешённые переходы из доменной модели; backend сохраняет независимую проверку.
4. Административная проекция комментариев включает внутренние записи и имя автора. Партнёрская проекция остаётся без изменений: она исключает внутренние записи и не раскрывает логин сотрудника.

## Risks / Trade-offs

- Сотрудник с `lead.manage` видит все лиды: существующая модель не хранит назначенного ответственного. Назначение лидов остаётся отдельным решением.
- Видимый партнёру комментарий сохраняется в переписке и доступен в карточке. Отдельный центр уведомлений ещё не реализован и в этой функции не имитируется.
