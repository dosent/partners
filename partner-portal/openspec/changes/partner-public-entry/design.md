## Context

Проект — существующее React/Vite SPA с Java/Spring Boot backend на том же origin. В production уже есть Yandex ID для партнёров, регистрация и статус заявки; сотрудники входят через LDAP. Регистрационный контент хранит один комплект юридических текстов на локаль. RBAC хранится приложением, а системный администратор может получить/заменить роли для конкретного логина. Полный целевой интерфейс описан в `docs/technical-specification-partner-portal.md` и общей спецификации OpenSpec.

Решения пользователя для этого изменения: интерфейс только на русском без RU/KZ/EN; отдельная текстовая оферта для физлица, ИП и юрлица управляется администратором; согласие на обработку ПДн общее; публичная страница нужна неавторизованному партнёру; админка должна позволять управлять пользователями с ролями.

## Goals / Non-Goals

**Goals:**

- Дать анонимному посетителю понятный вход в партнёрскую программу.
- Не менять утверждённые потоки Yandex ID, ручной проверки и безопасного статуса заявки.
- Показывать и фиксировать оферту, соответствующую выбранному типу партнёра.
- Упростить администрирование уже назначенных ролей и выдачу ролей новому логину.

**Non-Goals:**

- KZ/EN и пользовательский переключатель языка.
- PDF, загрузка файлов, S3 и rich-text HTML для оферт.
- LDAP-каталог/поиск всех сотрудников и выдача прав по LDAP-группам.
- Реализация остальных доменных разделов кабинета (лиды, финансы, staffing, документы).
- Автоматическая проверка реквизитов или автоматическое решение по заявке.

## Decisions

### 1. Маршрутизация публичного входа

Корневой маршрут `/` показывает публичный лендинг, если у посетителя нет партнёрской сессии. CTA регистрации ведёт на `/registration`; вход запускает существующий Yandex ID flow. После возврата от провайдера пользователь попадает в текущую форму/статус заявки. Сотруднический контур остаётся на `/staff` и не смешивается с партнёрской авторизацией. Одобренные партнёры продолжают попадать в существующий кабинет.

Лендинг использует краткий фактический текст о подаче заявки и ручной проверке, без демонстрационных метрик, обещаний дохода и неутверждённых юридических утверждений. Он наследует визуальный язык текущего портала.

### 2. Русский интерфейс

Публичный лендинг, форма, кабинет и рассматриваемая админка показывают русский интерфейс без переключателя локали. Для публичной регистрации используется русская версия контента (`ru`). Удаление пользовательского переключателя не должно удалять существующие данные локализации миграцией.

### 3. Оферты по типу заявителя

В черновике регистрационного контента хранится отдельная тройка `offer` для `INDIVIDUAL`, `SOLE_PROPRIETOR` и `LEGAL_ENTITY`; у каждого элемента есть версия, заголовок и простой текст. Общая версия и текст согласия на обработку ПДн остаются едиными. Администратор `localization.manage` редактирует все три оферты и публикует согласованный комплект. Пустая оферта блокирует публикацию.

Публичный API отдаёт комплект опубликованных оферт. Форма сначала требует выбрать тип заявителя и отображает только соответствующую ему оферту с полным текстом и общей политикой ПДн. При submit клиент передаёт тип, версию и SHA-256 выбранной оферты, версию и SHA-256 общего согласия и отметки согласия. Backend повторно проверяет соответствие типа и опубликованных редакций; клиентская версия не является источником истины. Сохранённая редакция заявки и consent snapshot сохраняют версии/хэши неизменяемыми.

Документы отображаются как обычный текст с сохранением переносов строк. HTML не исполняется. Новая редакция не изменяет уже сохранённую редакцию согласия.

### 4. Управление пользователями и ролями

Админка показывает логины, у которых есть хотя бы одно назначение RBAC, с текущими ролями и поиском по логину. Системный администратор может открыть запись, заменить выбранный набор разрешённых ролей или начать назначение для нового логина. Новый логин вводится вручную; это соответствует текущему LDAP adapter, который умеет проверять введённые учётные данные, но не содержит настроенного LDAP directory-search service account/API.

Backend предоставляет ограниченный `staff.access.manage` endpoint для списка назначений. Чтение и замена ролей конкретного логина остаются серверно защищены. Удаление `SYSTEM_ADMIN` у bootstrap `ivan.neshin` остаётся запрещённым действующим policy. Все изменения продолжают создавать audit записи. UI не трактуется как граница безопасности.

### 5. Пустые состояния и production-данные

Никакие примеры компаний, метрик, назначений, переводов или оферт не seed-ятся в production. При отсутствии опубликованных оферт форма сообщает, что регистрация временно недоступна; лендинг остаётся доступным. Список ролей показывает честное пустое состояние, если назначений нет.

## Risks / Trade-offs

- Неполный текст одной из трёх оферт блокирует публикацию всего комплекта → показывать администратору точный перечень недостающих полей.
- Ручной ввод логина может ошибочно создать назначение для несуществующей учётной записи → подтверждать логин перед сохранением и сохранять действие в аудите; автоматический LDAP lookup не реализуется без отдельного directory API.
- Фиксация только текста и версии без hash может неверно описать согласованный документ → рассчитывать checksum на сервере для канонического текста и возвращать его в опубликованном API.
- Прямой вход по старому bookmarked `/registration` должен работать → оставить отдельный маршрут формы и текущую post-login навигацию.

## Migration Plan

1. Расширить модель draft/publication для трёх отдельных оферт и общего согласия; сохранить совместимость чтения старых `ru` публикаций либо закрыто отказать, если нет полного нового комплекта.
2. Обновить запросы регистрации и consent snapshot, чтобы проверить и записать hash оферты выбранного типа.
3. Добавить read-only список RBAC-назначений и подключить его к staff access screen.
4. Добавить лендинг и маршруты SPA; удалить переключатели RU/KZ/EN из этих экранов.
5. Включать регистрацию только при наличии всех утверждённых русских оферт, общего согласия и логотипа. Переключение назад выполняется возвратом к предыдущей версии приложения; аудит и consent snapshots не удаляются.
