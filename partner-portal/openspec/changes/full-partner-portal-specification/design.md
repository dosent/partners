## Context

См. `proposal.md` — Why. Текущий React/Vite прототип реализует кабинет партнёра с мок-данными в памяти. Активный change `partner-registration` уточнил внешний вход через Yandex ID, LDAP для сотрудников, ручную локализацию и отказ от локальных паролей/2FA. Целевой backend ещё отсутствует. Пользователь выбрал модульный монолит и отдельно запретил любые хранимые процедуры.

## Goals / Non-Goals

**Goals:**

- создать понятные границы доменных модулей внутри одного развёртываемого backend;
- обеспечить серверный RBAC, транзакционность, аудит и воспроизводимые расчёты;
- использовать JPA для агрегатов и JDBC для сложных чтений без дублирования ответственности;
- сохранить существующую визуальную основу и превратить все демонстрационные сценарии в реальные;
- позволить выделять модули в сервисы позднее без преждевременной распределённой архитектуры.

**Non-Goals:**

- микросервисное разбиение в первой версии;
- хранимые процедуры, `SimpleJdbcCall`, бизнес-логика в БД;
- локальные пароли и 2FA партнёров;
- автоматический перевод юридического или интерфейсного контента;
- автоматическое юридически значимое подписание без отдельно выбранной КЭДО-интеграции.

## Decisions

### 1. Модульный монолит

Backend — одно Spring Boot приложение с пакетами `access`, `partner`, `lead`, `staffing`, `candidate`, `finance`, `document`, `notification`, `localization`, `audit` и `integration`. Каждый модуль содержит `api`, `application`, `domain` и `infrastructure`; обращения к другому модулю идут через его application interface или доменное событие. Прямой доступ к repository другого модуля запрещён.

Альтернатива — микросервисы — отклонена из-за стоимости распределённых транзакций и эксплуатации на текущем масштабе. Неразделённый layered monolith отклонён, потому что со временем смешивает модели и права разных доменов.

### 2. Один web origin и контракт API

React/Vite SPA и `/api/v1` публикуются под одним origin. Backend является источником истины для прав, статусов и расчётов. DTO API — Java records; все операции документируются SpringDoc OpenAPI. Ошибки имеют единый envelope: `timestamp`, `status`, `code`, `message`, `traceId`, `fieldErrors`.

Контроллеры только валидируют transport-формат, вызывают application service и преобразуют ответ. Авторизация выполняется на method/security и application policy уровнях; переданный клиентом ID никогда не определяет область доступа сам по себе.

### 3. JPA для записывающей модели, JDBC для специализированного чтения

Spring Data JPA/Hibernate используется для агрегатов, CRUD, optimistic locking и связей внутри модуля. `NamedParameterJdbcTemplate` вместе с `QueryHelper` используется для сложных фильтров, дашбордов, финансовых реестров, аналитики и массовых обновлений, где JPA создаёт неясный или неэффективный SQL. SQL хранится в `src/main/resources/sql/<module>/` и регистрируется через enum `SqlQuery`.

JPA entity не передаётся через API и не используется как межмодульный контракт. Один use case имеет одного владельца транзакции. Смешивание JPA и JDBC в одной транзакции допускается только через один DataSource/transaction manager и покрывается интеграционным тестом.

Хранимые процедуры и `SimpleJdbcCall` запрещены без исключений. DDL выполняется только Liquibase; бизнес-логика остаётся в приложении.

### 4. Модель данных и конкурентность

Основные агрегаты: `UserIdentity`, `PartnerApplication`, `Partner`, `Lead`, `StaffingRequest`, `CandidateProfile`, `CandidateProposal`, `RewardAccrual`, `FinancialDispute`, `DocumentMetadata`, `Notification`, `LocalizedContentVersion`, `AuditEvent`.

История решений, статусов, согласий, финансовых расчётов и публикаций хранится append-only. Изменяемые агрегаты используют `@Version`. Команды approve/reject, подтверждение кандидата и финансовое согласование проверяют ожидаемую версию; конфликт возвращает `409 CONCURRENT_MODIFICATION`.

### 5. Аутентификация и безопасность

Партнёры используют Yandex ID OAuth 2.0 Authorization Code Flow; identity моделируется как `provider + subject`, что допускает новых провайдеров. Сотрудники используют LDAP; группы сопоставляются внутренним ролям конфигурацией. Backend создаёт HttpOnly/Secure/SameSite сессию, включает CSRF-защиту и не передаёт external access token в SPA.

Чувствительные реквизиты шифруются на уровне приложения или managed storage; для дедупликации используется нормализованный keyed hash. В логах значения маскируются. Проверка файлов включает allow-list типов, размер, контрольную сумму и антивирусный статус.

### 6. Доменные события и уведомления

После успешной доменной транзакции событие записывается в transactional outbox. Фоновый publisher доставляет уведомления и интеграционные сообщения с retry и dead-letter состоянием. Это не превращает приложение в микросервисы, но отделяет сбой дополнительного канала от основной операции.

### 7. Интеграции

Внешние системы инкапсулируются за typed interfaces и WebClient adapters: Yandex ID, государственные реестры, CRM, КЭДО, курсы валют и опциональный анализатор ТЗ. Каждый adapter имеет timeout, retry только для безопасных операций, circuit breaker, метрики и contract tests. Недоступность реестра ведёт к ручной проверке; недоступность уведомлений — к повторной доставке.

### 8. Frontend

Существующая визуальная композиция сохраняется. SPA получает route-level страницы: публичная часть, регистрация/статус, партнёрский кабинет и back-office. Server state хранится через единый data-access layer; формы используют общую валидацию и отображение ошибок API. Route guards улучшают UX, но не заменяют серверную авторизацию.

### 9. Поставка и качество

Backend собирается Gradle, frontend — Vite. Docker Compose поднимает frontend, backend, PostgreSQL, S3-compatible storage и тестовые adapters. Production развёртывается в Kubernetes минимум в трёх экземплярах backend; состояние хранится вне pod. Секреты поступают только в runtime.

Тестовая пирамида: unit tests для domain/application, `@DataJpaTest` для JPA, JDBC integration tests с PostgreSQL Testcontainers, MockMvc/API authorization tests, WireMock contract tests и Playwright end-to-end для критических RU/KZ/EN сценариев. Нагрузочные и security проверки входят в release gate.

## Risks / Trade-offs

- [Модули могут превратиться в формальное разделение пакетов] → запретить cross-module repository access и добавить архитектурные тесты ArchUnit.
- [JPA и JDBC могут расходиться по модели данных] → назначить модуль владельцем таблиц, хранить SQL рядом с модулем и запускать интеграционные тесты на реальном PostgreSQL.
- [Внешние реестры и КЭДО могут не иметь стабильного sandbox] → использовать adapters, stubs и feature flags; production-включение проводить отдельно.
- [Финансовые ошибки имеют высокий ущерб] → versioned rules, двойное подтверждение, идемпотентность и append-only audit.
- [Объём полного портала слишком велик для одного релиза] → реализовывать вертикальными этапами при общей модели и API-контрактах.

## Migration Plan

1. Зафиксировать OpenAPI, доменную модель и модульные границы; подготовить каркас backend и инфраструктуру.
2. Реализовать access/registration и перенести change `partner-registration` в общий контракт.
3. Подключить профиль и лиды, затем staffing/candidates.
4. Подключить finance/documents/notifications и профильные back-office очереди.
5. Подключать внешние интеграции через feature flags после contract/security review.
6. Провести миграцию с пустой production БД; демоданные не переносятся. Rollback выполняется возвратом версии приложения при обратносуместимой схеме; destructive migrations выпускаются отдельными expand/contract этапами.
