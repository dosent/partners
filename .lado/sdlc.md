# Настройки sdlc

Настройки проекта для LADO. Неуточнённые значения ниже требуют решения человека перед соответствующим шагом; не подставлять догадки.

## Languages

- Чат с человеком: русский (`ru`).
- Описания pull request и комментарии: русский.
- Комментарии в трекере: русский.
- Коммиты: английский, Conventional Commits (`feat(scope): subject`, `fix(scope): subject`, `test(scope): subject`, `docs(scope): subject`), как в истории проекта.
- Документы OpenSpec и проектная документация: русский; обязательные заголовки и ключевые слова OpenSpec сохранять на английском.

## Git

- Remote: `origin`, `git@gitlab.simbirsoft.com:ivan.neshin/partners.git`.
- Базовая ветка: `main`.
- Ветки задач всех масштабов: `codex/<key>-<slug>`, отдельный worktree от актуальной `main`.
- `<key>`: ключ задачи, преобразованный по правилу навыка `sdlc-settings`.
- Ветки эпиков: соглашение не задано; перед использованием уточнить у человека.
- Хостинг: GitLab (`gitlab.simbirsoft.com`). CLI: `glab`; наличие и авторизацию проверять перед операциями с merge request.
- Push требует отдельного явного поручения человека. Начало работы над задачей само по себе не разрешает push.

## Checks

| Команда | Рабочий каталог | Назначение |
|---|---|---|
| `npm ci` | `partner-portal` | Установка зависимостей по lockfile |
| `npm run build` | `partner-portal` | Сборка frontend |
| `npm run test:sites` | `partner-portal` | Проверки Sites, когда затронут этот слой |
| `./gradlew build` | `partner-portal/backend` | Сборка и тесты backend при изменениях backend |
| `npm run verify:e2e-ci` | `partner-portal` | Проверка конфигурации e2e в CI |
| `npm run test:e2e` | `partner-portal` | Обязательный полный браузерный набор в отдельном Docker Compose-проекте |
| `openspec validate --specs --strict` | `partner-portal` | Проверка спецификаций; установленный CLI и его доступность проверить перед использованием |

- Порядок, согласованный человеком: применимые unit/API/integration-проверки → обязательный браузерный e2e → коммит feature-ветки → отдельно разрешённый push и GitLab MR → ревью → одобрение слияния человеком → merge commit через MR → обновление локальной `main` через `git pull --ff-only`. Предварительная интеграция в локальную `main` не выполняется. До успешного e2e интеграция запрещена.
- Для нового или изменённого поведения нужны e2e основного пути и существенных отказов по доступу, состоянию или интеграции.
- E2E использует только искусственные данные; production credentials и данные запрещены.
- Исключения: Sites-проверки нужны при изменении соответствующего слоя; backend-проверки — при изменении backend. Браузерный e2e не заменяется другими проверками.
- CI: `.gitlab-ci.yml` запускает `verify:e2e-ci` и `test:e2e` для веток и merge request. Отдельные build/unit/lint jobs в текущем файле не заданы.
- Диагностика CI: `partner-portal/playwright-report/` и `partner-portal/test-results/`, включая обезличенные логи Compose; срок хранения 7 дней.
- Максимальное ожидание CI: не согласовано; уточнить перед ожиданием CI в запуске.

## External reviewer

- Внешний reviewer, команда вызова, признак завершения, максимальное ожидание и число раундов пока не настроены.
- До внешнего ревью запросить эти значения у человека; не имитировать успешное внешнее ревью.

## Review traps

- Успешные unit/API/Sites-тесты не доказывают работу браузерного сценария: требовать успешный полный e2e в feature worktree.
- Успешный pipeline не доказывает отдельный прогон backend unit/build: смотреть фактический состав jobs и результаты применимых локальных проверок.
- OpenSpec находится в `partner-portal/openspec`, а не в корне репозитория: выполнять команды из `partner-portal`.
- GitLab e2e job использует Docker-in-Docker: runner требует privileged-режима; сбой инфраструктуры не считать успешной проверкой продукта.
- Не связывать существующие изменения OpenSpec с новой задачей без подтверждённой связи.

## Extra instructions

- Соблюдать `AGENTS.md`; сохранять существующие пользовательские изменения.
- Supervisor не меняет код. Запускает только названные человеком задачи, по одному flow `task` и worktree на задачу.
- Не выполнять force-push, сброс рабочей копии, удаление веток или переписывание опубликованной истории без прямого поручения человека.
- Человек согласовал для PAR-1 процесс через GitLab MR вместо предварительной интеграции в локальную `main`: локальная `main` обновляется после слияния MR. Это явное исключение из порядка локальной интеграции в `AGENTS.md`. Push по-прежнему требует отдельного явного поручения по готовым изменениям.
- Секреты не хранить в Git, документации, аргументах команд или логах. Использовать runtime environment или secret store.
- Партнёры входят через Yandex ID, сотрудники — через LDAP; локальные пароли партнёров требуют отдельного утверждённого требования.
- Каждое развёртываемое приложение упаковывать в Docker; локальный запуск и интеграционные проверки выполнять через Docker Compose.
